> บทนี้ไม่ได้เขียนจากการอ่าน documentation แต่เขียนจากการ **query ฐานข้อมูลจริง** บน phon-server

## 1. จุดตั้งต้น: ทำไมต้อง self-host

พรไม่ได้เริ่มจาก "อยากลองเครื่องมือใหม่" แต่เริ่มจากปัญหาที่ทุกคนที่ทำงานคนเดียวเจอ:

**งานมีมากกว่าคน แต่ละงานต้องการความจำคนละแบบ**

- เก็บไอเดีย — ต้องจำว่าอะไรเข้าแล้ว อะไรยังไม่คัด
- ย่อยคลิป YouTube — ต้องจำว่าแถวไหนสรุปแล้ว
- วิจัยข่าว — ต้องจำว่าแหล่งไหนเชื่อได้
- เขียน content — ต้องจำเสียงของตัวเอง
- คุมหนังสือ 251 เล่ม — ต้องจำว่าอ่านถึงบทไหน

ถ้าใช้ AI ตัวเดียวจบ มันจะจำทุกอย่างปนกัน และเสียงจะเพี้ยน

**ทางออกคือแยกเป็นทีม** — แต่ละตัวมี "สมอง" (memory) และ "กฎ" (rules) ของตัวเอง
Rakazo ให้โครงสร้างนี้มา พรจึงเลือก self-host บน `phon-server` ไม่ใช่ cloud

## 2. สถาปัตยกรรมจริง (ยืนยันจากของจริง)

```
phon-server
└── ~/rakazo  (deployment dir — ไม่ใช่ git repo)
    ├── .env
    ├── docker-compose.images.yml
    └── containers:
        ├── rakazo-web-1         UI
        ├── rakazo-api-1         API
        ├── rakazo-worker-1      รันงานเบื้องหลัง
        ├── rakazo-supervisor-1  คุม sandbox
        ├── rakazo-postgres-1    ฐานข้อมูล
        └── rakazo-bot-team-…    ที่อยู่ของบอท (computer image)
```

**จุดสำคัญที่คนมักเข้าใจผิด:** `Rakazo.app` บน Mac เป็นแค่ **PWA shortcut** ชี้ไปที่ `https://phon-server.scorpion-tint.ts.net/`
ไม่มี state อะไรอยู่ในเครื่อง Mac เลย — ข้อมูลจริงทั้งหมดอยู่ใน container บน server

**ทางเข้าเดียว:** `https://phon-server.scorpion-tint.ts.net/`

## 4. กฎของบอทถูกกำหนดยังไง (3 ชั้นซ้อนกัน)

นี่คือส่วนที่ตอบคำถาม "กำหนดกฎให้บอท" — Rakazo ให้ 3 ชั้น และพรใช้ทั้ง 3

### ชั้นที่ 1 — Description (บทบาทสั้น)

กำหนดตอนสร้างบอท 1-2 ประโยค บอกว่า "ดูแลอะไร" + "ห้ามอะไร"

ตัวอย่างจริงจาก `bots` table:

> **Book Keeper** — ดูแลฐาน Books Library ใน Notion (workspace lifetofree): หนังสือใหม่ 251 เล่ม — เพิ่ม/แก้แถว, กรองหนังสือตามระดับพลังงาน G.1–G.3/Boss, คุม vocabulary ของ Tags, ดูแลสถานะการอ่านรายบท (chapter) และรายงานหนังสือที่อ่านจบ — **ห้ามแตะไฟล์ใน repo โดยไม่ได้รับอนุมัติ**

> **Product Lead** — ควบคุมดูแลการผลิต product ของ adduckivity (เช่น e-book): ติดตามการ์ด Type=Product ในฐาน Idea, วางแผนแตกบท + จัดคิวผลิต, มอบงานเขียนให้ Adduck Writer, ตรวจคุณภาพก่อนส่งมอบ — **ห้าม publish เอง**

**สังเกต:** ทุกตัวที่มีอำนาจแตะของจริง จะมี "ห้าม" ต่อท้ายเสมอ นี่คือการออกแบบ ไม่ใช่ความบังเอิญ

### ชั้นที่ 2 — MEMORY.md ของบอท (ความรู้ถาวร)

แต่ละบอทมีไฟล์ `MEMORY.md` ของตัวเองใน `memory_documents` (scope = `bot`)

ขนาดจริง ณ วันนี้:

| บอท | MEMORY.md |
|---|---|
| Chief | 4,942 chars |
| Book Keeper | 3,666 chars |
| Adduck Writer | 1,985 chars |
| Research Distiller | 809 chars |
| Product Lead | 489 chars |
| Idea Keeper / Research Scout / Stall Watcher / Design Keeper | 89–93 chars (ยังว่าง) |

**สิ่งที่สังเกตได้:** บอทที่ทำงานซับซ้อนที่สุด (Chief, Book Keeper, Adduck Writer) มี memory ใหญ่สุด
บอทที่เพิ่งสร้างหรือทำงานแคบ ยังไม่มีอะไรให้จำ

### ชั้นที่ 3 — Routine (งานตามเวลา / งานที่สั่งซ้ำ)

มี 9 routines ทั้งหมด — และ **ทั้ง 9 ตัว `active = false`**

นี่คือข้อมูลสำคัญ: **พรใช้ routine เป็น "แผนงาน" มากกว่า "cron ที่วิ่งเอง"** — ตั้งไว้เป็นบันทึกว่าต้องทำอะไร แล้วสั่งรันมือเมื่อพร้อม

ตัวอย่างชื่อ routine จริง:
- `ตรวจเช้า 18 พ.ย. (SLT + ice bath + mockup)`
- `แก้คิว: ยิงบรีฟ Body คั่น 14 หน้า (คำสั่ง Phon 10:04) ให้ PL + ปิดจุดค้าง ping 09:41`
- `เช็คส่งมอบบท AW (e-book Rakazo)`

**สิ่งเหล่านี้คือ log การทำงาน ไม่ใช่ automation** — ชื่อบอกวันที่และคำสั่งเฉพาะ แปลว่ามันเกิดจากงานจริงไม่ได้ออกแบบล่วงหน้า

## 5. การเชื่อมต่อ: Notion เป็นศูนย์กลาง

**นี่คือหัวใจของทั้งระบบ**

`connections = 0` แตะ `mcp_servers = 2` — แปลว่าพรไม่ได้ใช้ integration สำเร็จรูป แต่ใช้ **MCP ต่อ Notion ตรง ๆ**

```
Rakazo bot → MCP (streamable_http) → https://mcp.notion.com/mcp → Notion workspace
```

MCP 2 ตัวชี้ **endpoint เดียวกัน** (`notion` และ `notion-mcp`) — เป็น setup ซ้ำที่ยังไม่ได้เก็บกวาด

**ฐาน Notion ที่ทีมใช้:**

| ฐาน | ใครใช้ |
|---|---|
| Idea (Kanban) | Idea Keeper, Stall Watcher, Product Lead |
| YouTube Library | Research Distiller |
| Knowledge Base | Research Scout |
| Content Drafts | Adduck Writer |
| Books Library | Book Keeper, Adduck Writer (อ่านเท่านั้น) |

**ผลลัพธ์:** ไม่มีฐานข้อมูลแยกใน Rakazo เลย — Notion เป็น single source of truth ทั้งหมด Rakazo ทำหน้าที่แค่ "คนทำงาน"

## 6. GitHub: ทางออกที่ต้องมี แต่ยังไม่เรียบร้อย

มี vault credential 2 ตัวสำหรับ GitHub (`github-token`, `github-phon-hermes-push`) — เพิ่มวันที่ 16 พ.ย.

**แต่ของจริงคือ:** git ใน container **ไม่ได้ใช้ credential จาก vault** — มันใช้ GitHub CLI (`gh auth git-credential`) ที่มี token ของตัวเองใน `~/.config/gh/hosts.yml`

**นี่คือรอยร้าวที่ทำให้เกิด 403 เมื่อวาน (19 พ.ย. 07:11)**

ระบบมี "ทางให้ token" สองทาง แต่ git เลือกใช้ทางที่ไม่มีใครดูแล

## 7. สิ่งที่พรเรียนรู้จากการใช้งานจริง (ไม่ใช่จาก docs)

### ✅ สิ่งที่เวิร์ก

1. **แยกบอทตาม memory ไม่ใช่ตาม function** — Idea Keeper กับ Stall Watcher ทำงานกับฐานเดียวกัน แต่ต้องการความจำต่างกัน
2. **ใส่ "ห้าม" ใน description ทุกครั้ง** — บอทที่ไม่มีข้อห้ามจะทำเกินขอบเขต
3. **Notion เป็นศูนย์กลาง** — ลดความซ้ำซ้อน ข้อมูลอยู่ที่เดียว
4. **สร้างเมื่อจำเป็น ไม่สร้างรอ** — 9 ตัวใน 4 วัน เกิดจากงานจริง

### ⚠️ สิ่งที่ยังเป็นหนี้

1. **routine 9 ตัวไม่มีตัว active** — ยังไม่มี automation จริง ถ้าลืมสั่ง = ไม่เกิด
2. **MCP ซ้ำ 2 ตัว** — `notion` และ `notion-mcp` ชี้ที่เดียวกัน เสี่ยงสับสน
3. **credential GitHub 2 ทาง** — vault มี แต่ git ไม่ได้ใช้ ← ต้นเหตุ 403
4. **บอท 4 ตัว memory ว่างเปล่า** (89–93 chars) — ยังไม่ได้ป้อนบริบท
5. **ไม่มีใครเฝ้า** — token ตาย 9 ชั่วโมงกว่าโดยไม่มีใครรู้

## 8. ถ้าจะเริ่มใหม่ ควรทำอะไรต่าง

จากสิ่งที่เห็น พรน่าจะทำแบบนี้ถ้าเริ่มใหม่:

1. **สร้าง Chief ก่อน แล้วให้ Chief รู้ว่ามีบอทอะไรบ้าง** — ตอนนี้ Chief มี memory ใหญ่สุด แต่ไม่รู้ว่าทีมมีใคร
2. **กำหนด "ห้าม" ตั้งแต่ description แรก** — ไม่ใช่เพิ่มทีหลังเมื่อบอททำพลาด
3. **credential ทางเดียว** — เลือกอย่างเดียวระหว่าง vault หรือ gh CLI ไม่ใช่ทั้งสอง
4. **เปิด routine สัก 1-2 ตัว** ให้เป็น automation จริง เพื่อพิสูจน์ว่าระบบเดินเองได้
5. **มีคนเฝ้า** — อย่างน้อยวันละครั้ง ตรวจว่า token ยังดี

## 9. บทเรียนที่ใหญ่กว่าระบบ

**Rakazo ไม่ได้แก้ปัญหาด้วยการให้ AI เก่งขึ้น แต่แก้ด้วยการแบ่งงานให้ชัด**

บอทแต่ละตัวไม่ได้ฉลาดกว่ากัน — แต่ละตัว **รู้แคบลง** จึงทำได้แม่นขึ้น

bอท 9 ตัวที่ทำงานคนละเรื่อง ไม่ได้แข่งกันเก่ง แต่แข่งกัน "ไม่ก้าวก่ายกัน"

นี่คือสิ่งที่คนทำธุรกิจคนเดียวเข้าใจดี: **ไม่ได้ต้องการคนเก่งที่สุด ต้องการคนที่รู้ว่าตัวเองทำอะไร**
