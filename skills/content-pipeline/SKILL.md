# Content Pipeline (adduckivity)

Use for any content drafting task for the adduckivity brand: research a topic, draft a post, file it in Notion, back it up on GitHub.

## Workflow (order matters)

**FORM SELECTOR — read this BEFORE any drafting rule below; it decides the form, the rest of the file is depth/provenance:**
- **Tech/tool-review brief** (a tool, product, benchmark, how-to) → v2 line-per-sentence TECH form (stat-line opener, comparison table, real benchmark + disclaimer, two-fork ending) — v2 is STILL ground truth for tech posts.
- **System/mindset brief** (an idea about work/habit/attention/decisions — the usual Thai idea brief) → **CURRENT FORM** (story opener, ONE dispatch question + 2 modes, worked example load-bearing, near-miss, zero protocols/tables/H2/Laws labels). Do NOT build 3-error sections or XX-0N protocols for these — that architecture is pre-#12 historical.
- **User pastes a Benz-DNA critique** → critique workflow (skeleton = new spine, critic lines verbatim, CUT zero-count, PATCH same page).
- **User pastes their own rewrite/"version ที่จะ publish"** → analyze-only flow (measure, archive, corpus entry; never edit their text). A paste byte-identical to the already-archived publish text is a NO-OP round: diff first, re-verify the Notion page state, and say so — do not re-grade or re-patch.
- **PASS-round critique (majority approved, small residue — pair #32 r2 pattern)** → freeze-list + removal-test round: archive + quote-verify + measure the freeze list (baseline counts) + corpus addendum + skill notes — do NOT rewrite or touch the page unless the user says so.
- **Agent is asked to CRITIQUE a draft in the Benz-DNA voice ("วิจารณ์ <draft>")** → the agent WRITES the critique: quote-verify every quoted line against the draft in code first (normalize whitespace/bold when comparing — expect full HIT), archive the critique verbatim to web-archive/ with measured BASELINES in its header (each named term's count = the acceptance marker the next round is graded against), commit, leave the draft untouched. A full-miss verdict ("evidence ยังไม่พอ") is a legitimate outcome — that critique ends with a BEFORE-NEXT-WRITE decision list (collect evidence first / park as night-question / cut), not a rewrite spec.
- **User asks for a review of a draft BEFORE sending it to Benz-DNA ("review ก่อนส่ง benz dna")** → pre-critique review, no edits: (a) run the standing draft-time battery in code (metrics, the header's own CUT zero-count list, codepoint + Thai–Latin adjacency scans, pronouns with negative lookahead); (b) verify the draft's header claims against the artifacts they cite — a reskin claim means reading the predecessor post's ACTUAL decision lines (its posts/ or web-archive file), never trusting the draft's description of them; (c) if the draft is already filed, Notion read-back (block count, derived markers, bold-quote annotations); (d) then apply the critique grammar PROACTIVELY to predict likely Benz points, ranked by likelihood — top of the list: a silent contradiction with a predecessor's published advice (the cross-post function audit catches it every time), a universal claim riding on N small cases, a hedge-then-pick pattern. Deliverable = gate table + ranked predictions + pre-publish items (e.g. story-seed ownership per EN #108) + a send-or-not verdict; the draft and the Notion page stay untouched until a real critique arrives.
- **User says "rewrite + ขอ title ใหม่" with NO critique** → RE-SPINE wholesale (rule in Notion specifics; applies to fresh drafts, not only steer rounds).
- **New draft in the Content Drafts DB from ANOTHER model** (a watchdog script `~/.hermes/scripts/notion_drafts_watcher.py` on a no_agent cron pings Telegram on new pages — cross-check its state file against a fresh DB query before calling anything "new") → intake = analyze-first: full battery (measure in code) + quote-provenance check (a book quote may already be verified in this skill's references/) + collision scan vs sibling posts; do NOT touch the draft or its Notion page until ordered. A rewrite request keeps the normal flow but with two overrides: write a NEW agent file in posts/ (never overwrite the other model's file), and archive their v1 verbatim to web-archive/ BEFORE editing; then PATCH the same Notion page keeping the v1 Name/title (only the body is swapped, Status → rewritten). Pair numbering continues across authors.
- **Observation brief (a real single case — a practice, a moment, something the user actually did; "เรามองเห็นอะไร"-style open question, no protocol/prescription asked)** → Observation post, EN #138 shape: scene (grounded ONLY in the user's own practice) → expectation → the anomaly moment → what actually appears → the question gets SMALLER and ends open. Rules: never invent micro-events inside the case — if the evidence window between event and noticing is empty, the CLOSING QUESTION names that window and declares the user will watch there next time (evidence-collection ending, not a missing answer); do not coin a NAME for what appeared unless the case forces it — point at the event instead ("ช่วงที่ X หลุด" beats a fresh noun); images must not imply a spectator the case doesn't have ("ฉากหลัง/background" implies someone watching — if the finding is that the narrator was NOT watching, pick the image that says so); no cross-ref to an earlier post with the same skeleton — tell it from this case only.
- Conflict rule: CURRENT FORM wins for system posts, v2 wins for tech posts; the older architecture layers in this file are historical depth, not competing menus.
- **Draft-time gates (run while writing, before filing):** (a) re-skin check — does the draft's core add a DECISION the predecessor lacked, or re-map 1:1 onto it? (b) thesis-stack check (EN #109) — for EVERY connection after the first, ask "ทำให้ Thesis เดิมชัดขึ้น หรือเปิด Thesis ใหม่?" — new-thesis connections get parked as กิ่ง in the HTML header, not in the body; (c) evidence ceiling (EN #110) — one case ⇒ hedged claim (บางครั้ง/หรือเปล่า); mechanism claims need more evidence or get cut; (d) killer-line counterexample hunt (EN #111); (e) the scene that makes the concept visible is the spine — end where the event ends, concept becomes the closing question (EN #112); (f) receipt/timeline check — every time-relative phrase in the story ("สัปดาห์ก่อน", "เดือนก่อน", "อีกไม่ถึงเดือน") is a CLAIM: verify it against the real event date (launch/research receipts) and keep the post internally consistent — two different relative anchors for the same event ("สัปดาห์ก่อน" vs "เดือนก่อน") read as a contradiction to the reader; when the real gap is long, either fix the phrase or name the event without a time anchor.

1. **Research from primary sources first.** Fetch official docs directly and verify facts before writing. `web_extract` may fail on some doc sites — for tailscale.com, `curl https://tailscale.com/docs/<path>.md` returns clean markdown (append `.md` to doc URLs). If `web_extract` is unavailable entirely (search-only backend error), fall back to fetching with **urllib inside `execute_code`**: `urllib.request.urlopen(Request(url, headers={'User-Agent':'Mozilla/5.0...'}))`, strip `<script>/<style>`, then tags → plain text. For **GitHub-hosted projects** skip HTML parsing entirely: `https://raw.githubusercontent.com/<org>/<repo>/<branch>/README.md` (clean markdown) + `https://api.github.com/repos/<org>/<repo>` (stars/forks/license) + `.../releases/tags/<tag>` (full release notes) — GitHub API needs a User-Agent header or it 403s. If the tool is installed/running locally (e.g. `--version`, `--help`, a live port from `ss -tlnp`), verify against the LOCAL install too — local ground truth beats docs. For **book/literary quotes in the brief** (user pastes a quote without a source): the quote itself is the search key — `web_search` the exact phrase to find a public-domain/primary PDF mirror, `curl -sL -o book.pdf <mirror>`, `pdftotext book.pdf book.txt` (poppler is on this host), then `grep -n -B8 -A8 '<phrase fragment>' book.txt` — confirm the quote verbatim AND capture the surrounding mechanism passage (how the book gets from the claim to the result); record author/year/section in the draft header. The mechanism passage is often the post's actual content, with the quote as the hook.
1a. **Disambiguate the research target BEFORE drafting.** Product names are often taken by several companies at once. If `web_search` returns multiple distinct products for the name, fire a `clarify` call with the candidates (recommended first) EARLY — it can run in parallel with continued research — and let the user's own clue in the request weight the recommendation. Drafting 12k chars on the wrong product is the expensive failure mode. This includes NICKNAMES and fragments in a brief's product list ("muse ai", a bare "o", "Studio"): search each name live before it goes into a post — a similar-sounding product already sitting in this skill's references/ is the trap, not the answer (familiarity bias fills an ambiguous name with the identity we happen to have researched).
1b. **Verify the user's own technical claims before building on them.** When the user's request contains concrete details (URLs, ports, commands, "just open http://host:PORT"), check them against the live machine (`ss -tlnp`, `tailscale status`, `tailscale serve --help` for the installed version) and official docs. If the user's mental model is subtly wrong (e.g. attributing to `serve` what actually comes from MagicDNS), explain the correction to the user FIRST, then adjust. The correction itself is often good content (make it a section). The same rule covers **bibliographic details**: a user-cited chapter number or section placement is a claim, not a fact — verify against a full table of contents (book summary sites / secondary TOCs) before asserting "chapter N" in the draft, and flag the correction in the response (e.g. "Ch. 5" → actually chapter 50 of Rework).
1c. **Verify brief-cited SSOT anchors before drafting.** Briefs often map each idea to Duck OS SSOT concepts ("สอดคล้องกับ Law #3 / Survival Checksum / Cache Cleaner Step 2"). Grep `~/hermes-agent/duck-os/` for each named anchor, record the verified file+line in the draft's HTML header, then use each principle in the body **UNLABELED** (no Law #N tags, no protocol names, no framework labels — the pairs #12–16 pattern) with the full mapping kept in the header comment as review scaffolding the user will likely cut. If an anchor does not exist verbatim in the SSOT, do not invent it — restate the closest real concept. If a brief bullet ends in a dangling fragment (an unfinished marker word), do not build on the fragment — exclude it, flag the exclusion in the reply, and let the user correct it.
2. **Read BOTH style layers** before drafting: (a) the distilled voice guide `~/hermes-agent/content-study/WRITING_STYLE_GUIDE.md` (adduck voice, Thai/English mix, closing with social links + hashtags: #Adduckivity #DuckOS …) AND (b) the living corpus analysis `~/hermes-agent/content-study/STYLE_CORPUS.md` (evidence-based: real hooks, protocol-name inventory, measured structure stats, Evolution Notes + weekly Updates appended by cron job weekly-wp-archive-sync) — the corpus is the fresher signal; when it contradicts the guide, follow the corpus and note it.
3. **Check for a series/partner post** in `~/hermes-agent/content-study/index.json` (list of 250+ posts with slug/title/date/link/file) — new posts often continue an earlier one; read the previous part from `posts/` first.
4. **Write the draft as markdown** in `~/hermes-agent/content-study/posts/` named `YYYYMMDD-cnt-<slug>.md`. Include an HTML comment header with ContentID placeholder, series, status, and verified source URLs.
**Default for system/mindset briefs = CURRENT FORM** (see CURRENT FORM section below); historical skeletons (System Diagnostic 3-error, medium/core Type-A) live in `references/formats-history.md`.

   **Third post type — Vision / Manifesto ("my vision and Duck OS" brief):** when the user gives a source (often a YouTube URL) + "in angle my vision and Duck OS", it is a personal vision/manifesto, NOT a System Diagnostic or tool review. The personal position MUST be grounded in the Duck OS SSOT `~/hermes-agent/duck-os/Main_Data_for_UDO.md` — First Principle (User ≠ Machine), the 3 Laws, the Power Test (ดึงอำนาจกลับ / don't rely on others as a load-bearing wall), Anti-Hype ("ถ้าอะไรเสียงดัง = ผิด"), Quiet Power, Scale with Stillness, Asset>Activity — not invented. Use the long-form heading structure + `## บทสรุปจากพร` closer, in a first-person conversational "พร" register.
   **Viral-design brief ("มีโอกาส viral", "viral content", or the user naming OTP / hook hormones):** never invent hook mechanics — pull them from the Duck OS SSOT: **OTP Framework** (Observation → Transformation arc: pain → desire) and **4 Hook Hormones** (Attention Shock / Emotional Trigger / Identity Lock-in / Curiosity Loop), both defined in `~/hermes-agent/duck-os/OPB_Core_System.md` §3 and `Main_Data_for_UDO.md` §3. If the brief references a framework by name you don't recognize, grep the SSOT first — the named framework always exists there. Apply as: (a) title + first line = Attention Shock, ideally a self-check question the reader answers against their own profile/history, (b) name the audience's behavior as a NEW identity label (Identity Lock-in — gives readers a word to tag friends with = free distribution), (c) open a counterintuitive claim as a Curiosity Loop and explicitly defer its answer to the end (completion rate), (d) one screenshot-able English pull-quote before the closer, (e) a same-day ≤5-minute CTA challenge (comment velocity in the first hour). Record the hormone→element mapping in the draft's HTML comment header so review can audit the design. Guard = Phon DNA Filter: hooks must name a real problem the reader recognizes in themselves; emotional bait made to optimize engagement violates the SSOT. When the user asks WHY the post can go viral, answer by mapping each element back to a hormone, then state plainly that distribution (timing, first-hour engagement, platform fit — strongest on text-first X/Threads) is the other half of the outcome.
**Personal-diagnostic transform (draft→publish pair #11, 2026-09-21 — "Show Your Work กลับด้าน"):** the 5TH format. When the user publishes a personal-diagnostic version of a system post (or asks for a personal/confession-angle system post), the draft should already be written as: (a) hook = internal confession / self-check ("ถ้า X ทำให้คุณ Y — คุณกำลังทำมันกลับด้าน"), stat demoted from title to a mid-post section; (b) narrative self = พร as the diagnostic case ("ช่วงหนึ่งพรเข้าใจ…ผิด" — FIRST time พร narrates a system post; กู/55555 self-deprecation allowed in this format ONLY); (c) ONE named pipeline as spine (e.g. `Doing → Evidence → Compile → Show`) restated in the closer; (d) 3 symptoms each ending in a BOLD named state (Work for Showing / Exhaust บังคับ Engine / Activity ไม่มี Evidence); (e) a Tiny Experiment section (7 วัน, time-budget, debug question) INSTEAD of the XX-0N protocol + Success Criteria — the anti-protocol stance ("ไม่ใช่ 'ต้องโพสต์ทุกวัน' / ไม่ใช่ 'ต้องใช้เวลา 11 นาที'") is itself the position; (f) ONE quoted rule; (g) zero cross-refs / zero protocol names; (h) layout: `---` hr between H1 sections, `.` beats doubled, `>` blockquotes carry every direct question, dash bullets → 0; (i) closer = pipeline restatement as bold defs + night question ("วันนี้ Core Engine ของคุณทิ้ง Evidence อะไรไว้?" + "ถ้าตอบได้ ค่อย Compile มัน") — NO Law line, NO EN pull-quote, NO CTA number. Sturgeon-style quotes: demote attribution ("มีประโยคที่ถูกอ้างถึงบ่อยว่า"), no year/venue. Engineering protocol draft stays the SOURCE asset; the personal post is the narrative derivative — same hashtags. Full 12-move analysis: STYLE_CORPUS.md `### 2026-09-21` pair #11.

**Full REWRITE (not a transform/trim):** when the user hands a rewrite brief with a NEW core + NEW spine and DEMOTED/CUT prior concepts and says to drop the old architecture ("ทิ้ง architecture เก่า"), the old draft's structure is DISCARDED — do NOT retrofit/trim the old skeleton. Build the new file from the new core spine; write it in the register the user names ("ภาษาของพร" / the user's own voice) FROM THE START, NOT the published เรา/คุณ register — the user's own personal-diagnostic rewrites (pairs #11–13) all run the full พร narrator, so when the brief says the user's voice, that IS the register (drafting in the published register then converting wastes a pass). Demote prior concepts to NAMED references ("X → Y" / "X ลดระดับเป็น Y") rather than deleting them; keep the new core as the single spine and leave one recompile-able asset line. **Social line-break format (standing user directive: future social/FB versions follow this pattern).** Measured on the llama.cpp draft→publish pair (STYLE_CORPUS.md): it is NOT a trim (pub = 1.04× draft words) but a full re-flow + re-architecture. Apply when drafting the social/FB version of any post: (1) one clause per line, ≤60 chars, blank line between thoughts, "." on its own line = beat break, ". [blank] ." before a heading = section break; (2) re-architect capability tours into a decision framework ("N สัญญาณว่า X เริ่มไม่พอ") — when-to-escalate, not what-it-does; (3) title = proof-point stat, not tool name; hook = invisible-presence/attention-shock reveal; (4) one `>` blockquote pair = setup question + payoff question; (5) "—" em-dash bullets, never "-"; (6) headings `#` sections / `## N.` numbered listicle / `### N.` profiles; (7) คุณ-heavy body, พร only in expert-credence lines, no ครับ (single คับ allowed inside the Law closer); (8) KEEP tables, real command blocks, real benchmark numbers + an honesty note, Pro Tips by level, Law closer, hashtag tail; (9) CUT project lore, star counts, release notes, series Part-N cross-links, ✅❌ emoji headings, TL;DR; (10) closer is always `# #สรุปแบบวิศวกรเป็ด` hash form even when the source long-form used `## บทสรุปจากพร`. First TECH-form instance measured on pair #37 (2026-10-06): a v2 TECH draft re-flowed the same way (487 wc-w ≈ 1:1 words, 117 "." beats, H1 sections with `.` blank `.` separators) — tables collapse into staged bold questions, and the publish register goes full-พร.

   4a. **Slice a long draft into platform paths when it's long (or the user says "แบ้งเป็นหลาย path" / "แบ่งเป็นหลาย path").** A single 1500+ word long-form doesn't fit every feed. Produce a companion `YYYYMMDD-cnt-<slug>-paths.md` in `posts/` with one section per platform: **FB** = medium ~700 words (headingless "." format, same as a medium Type-A), **IG Carousel** = ~10 slides (hook → one idea each → CTA+sign-off), **X thread** = ~10 tweets numbered `N/` (hook first, hashtag core last), **Threads** = ~8 posts. Keep each platform's version self-contained (re-state the hook; don't say "as I said before"). File the paths file as a **separate Notion draft page** (companion to the main long-form — the long-form and its paths are two distinct Drafts pages, like a long-form + short version). This mirrors the Duck OS SSOT `/slice` and `/split` commands.
4b. **Scan the draft for foreign-script leakage before committing or pushing to Notion.** The local LLM drafting Thai occasionally emits Japanese-Kana / CJK / Korean tokens inside Thai sentences — caught twice in one session (a Japanese adverb in a draft body, a Chinese phrase in a STATE.md edit), and they pass every Thai-language check. Run a codepoint-range scan over the whole file (JP kana 0x3040–0x30FF, CJK 0x4E00–0x9FFF, Hangul 0xAC00–0xD7AF) in `execute_code` — no dictionary needed, works where pythainlp is unavailable; fix every hit before the commit. The same scan is the fallback for the known Thai sara-aa misspell class when the dict check can't run. **The codepoint scan is blind to Latin-script intrusions** — non-English foreign words spelled in Latin letters (e.g. an Indonesian adverb in a Thai sentence) pass every check; the scan has caught CJK leaks in 3 consecutive drafts, so after fixing the codepoint hits also do one quick re-read of the body for foreign non-English words. Also re-verify cross-referenced post DATES against index.json — a wrong year in a cross-ref is as visible to the reader as a typo. Add a **Thai–Latin adjacency scan**: `re.findall(r'[ก-๙][A-Za-z]|[A-Za-z][ก-๙]', body)` flags missing spaces at script boundaries (a Latin token glued onto Thai) — invisible to the codepoint scan and to Thai spellcheck; verify each hit by context before inserting the space.
4c. **Analyze-only requests ("analyze" the user's OWN draft, no "แก้/ปรับ/fix" asked).** When the user pastes their own draft (often a to-be-published version of one of our drafts) and asks to analyze it, the deliverable IS the analysis — (a) identify the format (which of the 6) and which earlier pair it extends; (b) MEASURE it in code against the source draft (wc-w, H1/H2, beats, em-dash bullets, blockquotes, protocol names, cross-refs, pronoun counts — never eyeball; pronoun counts need context filtering — พร is a substring of พร้อม/เพราะ, คับ of บังคับ); (c) map which points of any external critique it implements; (d) list nits as NOTES, not edits. Do NOT edit the post, Do NOT re-file to Notion unless asked; archive verbatim to `web-archive/`, append the pair analysis to STYLE_CORPUS.md `## Updates`, and record the user's decision (e.g. "post as-is") in the entry. "เก็บเป็นข้อมูล" = the corpus entry is the deliverable. **"อันนี้ที่ปรับแล้ว" / "analyze แล้วเอาไปปรับใช้ด้วย" (pair #14 flow, 2026-09-23):** the user returns the ADJUSTED full text of a draft UDO just filed to Notion, then asks to analyze + apply the learnings. Workflow: (1) if the adjusted text is a FULL replacement → PATCH the EXISTING page (properties Status→`rewritten` + Name/Topic updated; markdown `replace_content`) — same URL survives — and read back (markers + old architecture gone); (2) archive the user's text verbatim to `web-archive/` AND add an `index.json` entry for the archive (title noting 'user-rewrite, pair #N', link = the patched Notion page, file = archive path) so corpus stats stay complete; (3) measure in code against the draft (full metrics table + named-framework survival check); (4) append the pair analysis (moves list + new rules for future drafts) to STYLE_CORPUS.md; (5) "เอาไปปรับใช้" = apply the new rules to THIS skill (patch the pair section + drafting guidance) so the next draft already embodies the pattern; (6) commit + push. Do NOT edit the user's text (nits = notes only — and before flagging a layout anomaly as a paste artifact, check SYSTEMATICITY: an N× regular repetition across the text is the user's own layout choice, a one-off is the artifact candidate); do NOT mint a protocol for the user's new concepts (the residue taxonomy / Asset Obsession stay unnamed). **"version ที่จะ publish" (pair #15 flow, 2026-09-23):** the user pastes the FINAL publish text of a UDO draft. Same workflow as "อันนี้ที่ปรับแล้ว" with two differences: (1) PATCH the existing page with Status → `rewritten` (do NOT mint a `published` status — the page is still in the Drafts DB; promotion to the Content DB happens only after the user says so); (2) the analysis measures the publish text against the LAST draft version (v4, not v1) — the delta is the publish edit itself. A publish version may also RE-SPINE wholesale on the same day (pair #28: ล็อก-spine → Decision-Stable/Default/Automation at 1.75×, biggest transplant on record) — measure old-spine vocabulary death (zero-count) AND which FUNCTION SLOTS survived with new words; the kept story gets re-mined for a new reveal line, not reused as a fixed hook. Then verify the publish cut: the user's standard cuts are the action scaffolding (signals lists / tables / experiments / success criteria / meta about the post itself) while the worked example EXPANDS — if a publish text still carries full scaffolding, expect another round; if the locked closer is present verbatim, the core is settled. The publish text's nits (missing spaces inside bold/quoted lines, e.g. "วันดีดีที่สุดมันมีไว้") are NOTES only — they are the user's own text going to a real platform.
5. **Commit + push to GitHub** (repo ~/hermes-agent, branch main) — standing rule for all file work.
6. **File drafts in Notion in the "Content Drafts" DB FIRST** (Status: draft), NOT the Content DB. Only promote to the Content DB (CNT pages) after the user reviews. Drafting straight into the Content DB caused a user correction. **When the user says "draft ล่าสุด" / "อันล่าสุด" without naming a file, resolve it to the newest file under `content-study/posts/` (the adduckivity drafts) — never to a user publish-rewrite in `web-archive/`** (those are the user's own to-be-published assets, not adduckivity drafts; filing one costs a misfile + archive + re-push cycle). If two candidates are close in date, ask before pushing. **Default = FILE a new post's draft page as soon as it is review-ready** (battery clean, angle approved by the user) — the Drafts DB is the user's reading surface, and holding a finished draft back "until told" produces a "ไม่เห็น draft ใน notion" complaint. The hold-and-wait posture applies only to PATCHING an existing page during critique rounds (the user has repeatedly scoped those out explicitly), never to creating new draft pages.
7. **Always verify a Notion write by reading it back** (GET the page + `GET /v1/blocks/{id}/children`) before telling the user it's there. Also give the user the direct page URL — "I can't see it in Notion" complaints are usually a stale view or a filtered DB view, and the URL settles it.
   Read-back pitfalls (learned 2026-09-03):
   - **Run all Notion calls via curl, not urllib, and prefer parsing a saved `-o` file over terminal stdout — but a response file can silently fail to land while the request SUCCEEDED** (curl prints `000` and the file is missing/empty while the full JSON sits on stdout): if the file did not land, parse stdout instead, and never retry an ambiguous create before the title idempotency search below — a blind retry duplicates the page. On this host `urllib.request` returns a misleading 401 "Authorization header must use the format Bearer <token>" even when the header bytes are clean — do NOT conclude the token is bad from a urllib 401 alone. Build the payload JSON with `execute_code` (keep the secret out of the shell), then `curl -d @/tmp/payload.json -o out.json -w '%{http_code}'`. **Every request carries `-H 'Notion-Version: 2022-06-28'`** — without it the API returns 400 `missing_version` even with a valid token (NOT a token problem). **PATCH needs an explicit `-X PATCH`** — with `-d`, curl defaults to POST → 400 `invalid_request_url`. Read-back = `curl … -o blocks.json` then `json.load` on the FILE. Terminal capture mangles control characters (newlines in code blocks → `JSONDecodeError`), so parse the saved file, never the captured output. Before any write, confirm the token with a cheap curl `GET /users/me`.
   - Blocks are paginated at 100/page: long posts exceed one page, so **follow `has_more`/`next_cursor`** and verify the tail (closing hashtags / final section) is present, not just the first 100 blocks. **Build the pagination query string correctly** (`?page_size=100`, then `&start_cursor=…`): a malformed URL (e.g. `?page_size=100?start_cursor=…`) still returns HTTP 200 with the FIRST page, so the loop looks successful while silently re-reading the same 100 blocks — every tail marker then reports a false MISS. Before trusting marker checks, assert the collected block count is >100 (or that `has_more` actually went false) for any post longer than ~100 blocks.
   - Collect ALL `rich_text` items per block (code blocks are multi-item); if a marker "isn't found" it is often inside a code block — check headings separately from body text.

Unescape the read-back (or compare against the escaped variant) before declaring a marker MISSING. **Emphasis never survives into `plain_text`** — `**x**` becomes a bold annotation and the asterisks vanish, so a `**`-quoted marker is a guaranteed false MISS; derive read-back markers with emphasis stripped or check `annotations.bold`. **Quote glyphs get normalized in read-back too** — the CURRENT FORM writes Thai quoted lines with curly quotes (“ ” ‘ ’) and Notion's `plain_text` returns straight quotes (" '), so a marker carrying curly quotes is a guaranteed false MISS against the un-normalized read-back. A batch of quote-only misses on an otherwise-complete page is this artifact, not a page defect.
   - Before declaring a read-back marker MISSING at all, re-check the marker string against the DRAFT SOURCE — the marker list itself can carry the typo (searching a paraphrase of a line reports a false miss on a page that is actually complete); a one-line `print(target in draft_text)` settles it.    - In `execute_code`, read local draft files with plain `open(path).read()` — the `read_file` tool returns `N|content` line-numbered output that needs fragile re-parsing.
   - **A "200" or valid JSON from a file on disk is NOT proof the request just succeeded.** A `/tmp` response file left over from a PREVIOUS session can be parsed as a live success while the current call actually failed (e.g. network down). Before trusting a parse, confirm the file exists AND was written by the current call (curl `-w '%{http_code}'` returning `000` + `curl: (6) Could not resolve host` = the request never reached the host — that is a local-DNS failure, NOT a token failure).
