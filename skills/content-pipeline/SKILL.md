# Content Pipeline (adduckivity)

Use for any content drafting task for the adduckivity brand: research a topic, draft a post, file it in Notion, back it up on GitHub.

## Workflow (order matters)

**FORM SELECTOR — read this BEFORE any drafting rule below; it decides the form, the rest of the file is depth/provenance:**
- **Tech/tool-review brief** (a tool, product, benchmark, how-to) → v2 line-per-sentence TECH form (stat-line opener, comparison table, real benchmark + disclaimer, two-fork ending) — v2 is STILL ground truth for tech posts.
- **System/mindset brief** (an idea about work/habit/attention/decisions — the usual Thai idea brief) → **CURRENT FORM** (story opener, ONE dispatch question + 2 modes, worked example load-bearing, near-miss, zero protocols/tables/H2/Laws labels). Do NOT build 3-error sections or XX-0N protocols for these — that architecture is pre-#12 historical.
- **Owner fires half-formed ideas by voice mid-session** (speech-to-text fragments, "ลองเอาไปกรุบดูละกัน") → voice-dump intake: archive the raw text under `content-study/voice-dumps/`, parse and class it (own case / park / candidate), treat it as MATERIAL not instructions — no drafting until an owner-confirmed case picks the branch (item 226).
- **User pastes a Benz-DNA critique** → critique workflow (skeleton = new spine, critic lines verbatim, CUT zero-count, PATCH same page). The DOMINANT loop of late 2026-10 (pairs #65–#69, four consecutive 0-fail closes): v1 draft → Benz r1 (agent ANALYZES ONLY — archive verbatim + quote-verify + baselines; do not rewrite) → the critique ends in ONE gate whose answer (a letter or a sentence) selects the axis → the OWNER authors the publish and sends it → grade against (a) archive-header baselines, (b) KEEP-list verbatim-or-function, (c) gate-axis DEAD checks (the un-chosen axis = 0 in publish), then PATCH the page Status → published. Write 'do-not-build / ห้ามเติมเครื่องมือ' into every fresh Signal-stage draft header by default — consecutive critiques enforced it. Publish versions may CHAIN (v1→v2→v3 same day) when the owner keeps expanding a real case into a no-case post — re-archive each as publish-vN, re-run the battery, delete+rebuild the same page, no new pair (items 291–293).
- **User pastes their own rewrite/"version ที่จะ publish"** → analyze-only flow (measure, archive, corpus entry; never edit their text). A paste byte-identical to the already-archived publish text is a NO-OP round: diff first, re-verify the Notion page state, and say so — do not re-grade or re-patch. The no-op applies only when the round is already CLOSED; a publish pre-archived as round STAGING (index status 'publish-archived — ยังไม่เกรด', staged to hold baselines before the text arrived) IS that round's ground truth — when the paste lands, diff against it, grade against the staged keys, and PATCH to published.
- **PASS-round critique (majority approved, small residue — pair #32 r2 pattern)** → freeze-list + removal-test round: archive + quote-verify + measure the freeze list (baseline counts) + corpus addendum + skill notes — do NOT rewrite or touch the page unless the user says so. The freeze list is the publish round's grading key; when the user later returns the publish version, run the round in this order: (a) archive the publish text verbatim FIRST (archive-before-grade is fixed), (b) grade every freeze-list term before→after in code in BOTH the file and the Notion read-back (old term 0, critic's replacement present) plus KEEP-list zero-drift — owner's-call keeps (the publish rejects a critic suggestion, e.g. a subtitle the critic wanted cut) are NOTES, not failures, (c) PATCH the same page with the publish body + Status → `published` (not `rewritten`), title changes via the Name property, then read back markers + CUT survivors + add the index publish-archive entry, (d) only then reverse engineering (publish moves → skill items) and the corpus CLOSED entry; the user may defer (d) — it folds into the CLOSED entry with no intermediate corpus/skill edits. **Grading a publish against the critique's kill/CUT list: judge SURVIVORS by function, not raw token** — a hit violates only when it carries the killed function; substring lookalikes (คับ inside บังคับ, ภัย inside ปลอดภัย) and critic-supplied uses of a banned word (the critic's own negated line "ไม่ได้บอกระดับอันตรายได้แม่นยำทุกครั้ง") pass — declare every exception in the header/corpus entry instead of arguing the scanner's raw count.** When a NEW critique arrives while a rewrite round sits unfinished, diff every quoted line against the CURRENT on-disk version first — if the quotes only match an ARCHIVED version, the critic re-saw the old draft (stale view), and the round is a NO-OP: verify the live page implements the critique's asks, say so with the page URL, do not re-grade or re-write (rule 43's quote-version diff is the enforcement tool).
- **Agent is asked to CRITIQUE a draft in the Benz-DNA voice ("วิจารณ์ <draft>")** → the agent WRITES the critique: quote-verify every quoted line against the draft in code first (normalize whitespace/bold when comparing — expect full HIT), archive the critique verbatim to web-archive/ with measured BASELINES in its header (each named term's count = the acceptance marker the next round is graded against), commit, leave the draft untouched. A full-miss verdict ("evidence ยังไม่พอ") is a legitimate outcome — that critique ends with a BEFORE-NEXT-WRITE decision list (collect evidence first / park as night-question / cut), not a rewrite spec.
- **User asks for a review of a draft BEFORE sending it to Benz-DNA ("review ก่อนส่ง benz dna")** → pre-critique review, no edits: (a) run the standing draft-time battery in code — use this skill's `scripts/draft_battery.py <draft.md> --cut "term1,term2"` (strips the HTML header, grades body+hashtags: wc-w, H1/H2/H3, beats, blockquotes, pronouns with negative lookahead, CUT survivors with exit 1, codepoint scan, Thai–Latin adjacency) instead of re-hand-rolling it per round — treat its pronoun/คับ output as CANDIDATE counts and verify every hit in context before acting on the number (the scanner over-counts lookalikes like บังคับ→คับ and can miss พร variants, so over- AND under-counts happen). **Thai tone marks sit BETWEEN the consonant and the vowel (พร้อม = พ-ร-้-อ-ม), so a naive `พร(?!อม)` lookahead never matches and reports phantom พร hits — build every พร-exclusion class with an optional tone-mark prefix (`[\u0E48-\u0E4B]?` before each vowel, e.g. `พร(?!้?อม|้?าะ|้?อง|...)`), then verify remaining hits in context; (b) verify the draft's header claims against the artifacts they cite — a reskin claim means reading the predecessor post's ACTUAL decision lines (its posts/ or web-archive file), never trusting the draft's description of them; (c) if the draft is already filed, Notion read-back (block count, derived markers, bold-quote annotations); (d) then apply the critique grammar PROACTIVELY to predict likely Benz points, ranked by likelihood — top of the list: a silent contradiction with a predecessor's published advice (the cross-post function audit catches it every time), a universal claim riding on N small cases, a hedge-then-pick pattern. Deliverable = gate table + ranked predictions + pre-publish items (e.g. story-seed ownership per EN #108) + a send-or-not verdict; the draft and the Notion page stay untouched until a real critique arrives.
- **Bare "rewrite draft" / "rewrite <slug>" with NO direction and NO critique** → do NOT re-spine on a guess: clarify the direction first (self-review + self-rewrite keeping the spine — the #46-r1/#48-r1 pattern — vs re-spine to a header candidate hook vs trim). Then: run the standing battery on the current file, snapshot the outgoing version to web-archive/ BEFORE overwriting (item 35), fix only what violates a form/corpus rule (keep the spine), log every fix in the HTML header, PATCH the same Notion page (check index.json by slug FIRST — see the duplicate-page pitfall under Notion specifics), and leave Status untouched on a pre-critique round (draft stays `draft`; `rewritten` is for critique/steer rounds only).
- **User says "rewrite + ขอ title ใหม่" with NO critique** → RE-SPINE wholesale (rule in Notion specifics; applies to fresh drafts, not only steer rounds).
- **New draft in the Content Drafts DB from ANOTHER model** (a watchdog script `~/.hermes/scripts/notion_drafts_watcher.py` on a no_agent cron pings Telegram on new pages — cross-check its state file against a fresh DB query before calling anything "new") → intake = analyze-first: full battery (measure in code) + quote-provenance check (a book quote may already be verified in this skill's references/) + collision scan vs sibling posts; do NOT touch the draft or its Notion page until ordered. A rewrite request keeps the normal flow but with two overrides: write a NEW agent file in posts/ (never overwrite the other model's file), and archive their v1 verbatim to web-archive/ BEFORE editing; then PATCH the same Notion page keeping the v1 Name/title (only the body is swapped, Status → rewritten). Pair numbering continues across authors.
- **OUTBOUND cross-model handoff (owner asks whether another model can continue a live pair on the same spine):** the FORM is portable (Content_Thinking_Playbook.md is model-agnostic) but a pair's SPINE is not — it lives in the pair's artifacts, not the playbook. Hand over exactly three things: the playbook, the CURRENT draft file (its HTML header carries what-changed/keeps/kills — the header IS the spine manual), and the latest critique archive + the owner gate answer in one line. A raw brief alone reproduces the PRE-critique draft's natural gravity (brief vocabulary pulls toward criteria-and-measurement skeletons the critique already killed) and drops rules like the lens-inversion gate. Answer this owner question with the package, not a bare yes.
- **Observation brief (a real single case — a practice, a moment, something the user actually did; "เรามองเห็นอะไร"-style open question, no protocol/prescription asked)** → Observation post, EN #138 shape: scene (grounded ONLY in the user's own practice) → expectation → the anomaly moment → what actually appears → the question gets SMALLER and ends open. Rules: never invent micro-events inside the case — if the evidence window between event and noticing is empty, the CLOSING QUESTION names that window and declares the user will watch there next time (evidence-collection ending, not a missing answer); do not coin a NAME for what appeared unless the case forces it — point at the event instead ("ช่วงที่ X หลุด" beats a fresh noun); images must not imply a spectator the case doesn't have ("ฉากหลัง/background" implies someone watching — if the finding is that the narrator was NOT watching, pick the image that says so); no cross-ref to an earlier post with the same skeleton — tell it from this case only.
- Conflict rule: CURRENT FORM wins for system posts, v2 wins for tech posts; the older architecture layers in this file are historical depth, not competing menus.
- **Draft-time gates (run while writing, before filing):** (a) re-skin check — does the draft's core add a DECISION the predecessor lacked, or re-map 1:1 onto it? (b) thesis-stack check (EN #109) — for EVERY connection after the first, ask "ทำให้ Thesis เดิมชัดขึ้น หรือเปิด Thesis ใหม่?" — new-thesis connections get parked as กิ่ง in the HTML header, not in the body; (c) evidence ceiling (EN #110) — one case ⇒ hedged claim (บางครั้ง/หรือเปล่า); mechanism claims need more evidence or get cut; (d) killer-line counterexample hunt (EN #111); (e) the scene that makes the concept visible is the spine — end where the event ends, concept becomes the closing question (EN #112); (f) receipt/timeline check — every time-relative phrase in the story ("สัปดาห์ก่อน", "เดือนก่อน", "อีกไม่ถึงเดือน") is a CLAIM: verify it against the real event date (launch/research receipts) and keep the post internally consistent — two different relative anchors for the same event ("สัปดาห์ก่อน" vs "เดือนก่อน") read as a contradiction to the reader; when the real gap is long, either fix the phrase or name the event without a time anchor.

1. **Research from primary sources first.** Fetch official docs directly and verify facts before writing. `web_extract` may fail on some doc sites — for tailscale.com, `curl https://tailscale.com/docs/<path>.md` returns clean markdown (append `.md` to doc URLs). If `web_extract` is unavailable entirely (search-only backend error), fall back to fetching with **urllib inside `execute_code`**: `urllib.request.urlopen(Request(url, headers={'User-Agent':'Mozilla/5.0...'}))`, strip `<script>/<style>`, then tags → plain text. For **GitHub-hosted projects** skip HTML parsing entirely: `https://raw.githubusercontent.com/<org>/<repo>/<branch>/README.md` (clean markdown) + `https://api.github.com/repos/<org>/<repo>` (stars/forks/license) + `.../releases/tags/<tag>` (full release notes) — GitHub API needs a User-Agent header or it 403s. If the tool is installed/running locally (e.g. `--version`, `--help`, a live port from `ss -tlnp`), verify against the LOCAL install too — local ground truth beats docs. For **book/literary quotes in the brief** (user pastes a quote without a source): the quote itself is the search key — `web_search` the exact phrase to find a public-domain/primary PDF mirror, `curl -sL -o book.pdf <mirror>`, `pdftotext book.pdf book.txt` (poppler is on this host), then `grep -n -B8 -A8 '<phrase fragment>' book.txt` — confirm the quote verbatim AND capture the surrounding mechanism passage (how the book gets from the claim to the result); record author/year/section in the draft header. The mechanism passage is often the post's actual content, with the quote as the hook.
1a. **Disambiguate the research target BEFORE drafting.** Product names are often taken by several companies at once. If `web_search` returns multiple distinct products for the name, fire a `clarify` call with the candidates (recommended first) EARLY — it can run in parallel with continued research — and let the user's own clue in the request weight the recommendation. Drafting 12k chars on the wrong product is the expensive failure mode. This includes NICKNAMES and fragments in a brief's product list ("muse ai", a bare "o", "Studio"): search each name live before it goes into a post — a similar-sounding product already sitting in this skill's references/ is the trap, not the answer (familiarity bias fills an ambiguous name with the identity we happen to have researched).
1b. **Verify the user's own technical claims before building on them.** When the user's request contains concrete details (URLs, ports, commands, "just open http://host:PORT"), check them against the live machine (`ss -tlnp`, `tailscale status`, `tailscale serve --help` for the installed version) and official docs. If the user's mental model is subtly wrong (e.g. attributing to `serve` what actually comes from MagicDNS), explain the correction to the user FIRST, then adjust. The correction itself is often good content (make it a section). The same rule covers **bibliographic details**: a user-cited chapter number or section placement is a claim, not a fact — verify against a full table of contents (book summary sites / secondary TOCs) before asserting "chapter N" in the draft, and flag the correction in the response (e.g. "Ch. 5" → actually chapter 50 of Rework).
1c. **Verify brief-cited SSOT anchors before drafting.** Briefs often map each idea to Duck OS SSOT concepts ("สอดคล้องกับ Law #3 / Survival Checksum / Cache Cleaner Step 2"). Grep `~/hermes-agent/duck-os/` for each named anchor, record the verified file+line in the draft's HTML header, then use each principle in the body **UNLABELED** (no Law #N tags, no protocol names, no framework labels — the pairs #12–16 pattern) with the full mapping kept in the header comment as review scaffolding the user will likely cut. If an anchor does not exist verbatim in the SSOT, do not invent it — restate the closest real concept. If a brief bullet ends in a dangling fragment (an unfinished marker word), do not build on the fragment — exclude it, flag the exclusion in the reply, and let the user correct it.
2. **Read BOTH style layers** before drafting: (a) the distilled voice guide `~/hermes-agent/content-study/WRITING_STYLE_GUIDE.md` (adduck voice, Thai/English mix, closing with social links + hashtags: #Adduckivity #DuckOS …) AND (b) the living corpus analysis `~/hermes-agent/content-study/STYLE_CORPUS.md` (evidence-based: real hooks, protocol-name inventory, measured structure stats, Evolution Notes + weekly Updates appended by cron job weekly-wp-archive-sync) — the corpus is the fresher signal; when it contradicts the guide, follow the corpus and note it.
3. **Check for a series/partner post** in `~/hermes-agent/content-study/index.json` (list of 250+ posts with slug/title/date/link/file) — new posts often continue an earlier one; read the previous part from `posts/` first.
4. **Write the draft as markdown** in `~/hermes-agent/content-study/posts/` named `YYYYMMDD-cnt-<slug>.md`. Include an HTML comment header with ContentID placeholder, series, status, and verified source URLs. **Drafting-header hygiene (owner directives 2026-10-20):** (a) NO real person names anywhere in the deliverable file — the editor/critic persona is referenced by ROLE ("critic", "รอบวิจารณ์"), never by name, in headers and body alike (owner: "ไม่อ้างอิงถึงชื่อคน เช่น Benz"); (b) internal system names (Hermes, profile names, home-server specifics) stay OUT of the post body — worked examples run class-level ("agent ตัวช่วยของพร") unless the owner explicitly opts in; the header's OWNER GATE note may carry the attested source privately.
**Default for system/mindset briefs = CURRENT FORM** (see CURRENT FORM section below); historical skeletons (System Diagnostic 3-error, medium/core Type-A) live in `references/formats-history.md`.
**Duck closer = H2 + NO H1 in Notion body (owner directives 2026-10-20, standing):** H1 belongs to the Title only — on WordPress the title renders as H1, so a Notion body must contain ZERO `heading_1` blocks; body headings start at H2 (`##`). The `#สรุปแบบวิศวกรเป็ด` closer is written `## #สรุปแบบวิศวกรเป็ด` and lands as `heading_2`; the doc-title `#` line maps to the Notion Name property and never to a body block; other in-body headings level down as appropriate (`###` subtitle stays heading_3). The Notion API cannot change a block's type — fix a wrong-level heading by DELETE block + PATCH children insert (block DELETE works in this workspace); quirk: `after` must go in the JSON BODY, `?after=` in the query string 400s with "query.after should be not present".
**Hashtags — default trio + beat before the tag line (owner directives 2026-10-20, standing):** every post carries `#Adduckivity #DuckOS #NeuroDivergent` as the DEFAULT tag trio; other tags are added as-fits after the trio (e.g. `#AI #SystemThinking`). The hashtag line is preceded by a `.` beat line — in the markdown file a blank line + `.` + blank line before the tags, and on the Notion page a `.` paragraph block immediately before the hashtag paragraph.
**Title ≡ dispatch-quote duplication = owner-call flag, never a silent call:** run an equality check between the title line and the body's `>` dispatch question before filing; when they match verbatim, flag it to the owner at draft time — the critic has frozen such a repeat as a defect (cut the quote or reword one side), yet the owner has also deliberately kept both in a publish, so a kept match is recorded as an owner-call NOTE in the corpus entry. Do not silently ship the duplication and do not silently cut the quote.

   **Third post type — Vision / Manifesto ("my vision and Duck OS" brief):** when the user gives a source (often a YouTube URL) + "in angle my vision and Duck OS", it is a personal vision/manifesto, NOT a System Diagnostic or tool review. The personal position MUST be grounded in the Duck OS SSOT `~/hermes-agent/duck-os/Main_Data_for_UDO.md` — First Principle (User ≠ Machine), the 3 Laws, the Power Test (ดึงอำนาจกลับ / don't rely on others as a load-bearing wall), Anti-Hype ("ถ้าอะไรเสียงดัง = ผิด"), Quiet Power, Scale with Stillness, Asset>Activity — not invented. Use the long-form heading structure + `## บทสรุปจากพร` closer, in a first-person conversational "พร" register.
   **Viral-design brief ("มีโอกาส viral", "viral content", or the user naming OTP / hook hormones):** never invent hook mechanics — pull them from the Duck OS SSOT: **OTP Framework** (Observation → Transformation arc: pain → desire) and **4 Hook Hormones** (Attention Shock / Emotional Trigger / Identity Lock-in / Curiosity Loop), both defined in `~/hermes-agent/duck-os/OPB_Core_System.md` §3 and `Main_Data_for_UDO.md` §3. Apply as: (a) title + first line = Attention Shock, ideally a self-check question the reader answers against their own profile/history, (b) name the audience's behavior as a NEW identity label (Identity Lock-in — gives readers a word to tag friends with = free distribution), (c) open a counterintuitive claim as a Curiosity Loop and explicitly defer its answer to the end (completion rate), (d) one screenshot-able English pull-quote before the closer, (e) a same-day ≤5-minute CTA challenge (comment velocity in the first hour). Record the hormone→element mapping in the draft's HTML comment header so review can audit the design. Guard = Phon DNA Filter: hooks must name a real problem the reader recognizes in themselves; emotional bait made to optimize engagement violates the SSOT. When the user asks WHY the post can go viral, answer by mapping each element back to a hormone, then state plainly that distribution (timing, first-hour engagement, platform fit — strongest on text-first X/Threads) is the other half of the outcome.

**Full REWRITE (not a transform/trim):** when the user hands a rewrite brief with a NEW core + NEW spine and DEMOTED/CUT prior concepts and says to drop the old architecture ("ทิ้ง architecture เก่า"), the old draft's structure is DISCARDED — do NOT retrofit/trim the old skeleton. Build the new file from the new core spine; write it in the register the user names ("ภาษาของพร" / the user's own voice) FROM THE START, NOT the published เรา/คุณ register — the user's own personal-diagnostic rewrites (pairs #11–13) all run the full พร narrator, so when the brief says the user's voice, that IS the register (drafting in the published register then converting wastes a pass). Demote prior concepts to NAMED references ("X → Y" / "X ลดระดับเป็น Y") rather than deleting them; keep the new core as the single spine and leave one recompile-able asset line. **Social line-break format (standing user directive: future social/FB versions follow this pattern).** Measured on the llama.cpp draft→publish pair (STYLE_CORPUS.md): it is NOT a trim (pub = 1.04× draft words) but a full re-flow + re-architecture. [blank] ." before a heading = section break; (2) re-architect capability tours into a decision framework ("N สัญญาณว่า X เริ่มไม่พอ") — when-to-escalate, not what-it-does; (3) title = proof-point stat, not tool name; hook = invisible-presence/attention-shock reveal; (4) one `>` blockquote pair = setup question + payoff question; (5) "—" em-dash bullets, never "-"; (6) headings `#` sections / `## N.` numbered listicle / `### N.` profiles; (7) คุณ-heavy body, พร only in expert-credence lines, no ครับ (single คับ allowed inside the Law closer); (8) KEEP tables, real command blocks, real benchmark numbers + an honesty note, Pro Tips by level, Law closer, hashtag tail; (9) CUT project lore, star counts, release notes, series Part-N cross-links, ✅❌ emoji headings, TL;DR; (10) closer is always `# #สรุปแบบวิศวกรเป็ด` hash form even when the source long-form used `## บทสรุปจากพร`. First TECH-form instance measured on pair #37 (2026-10-06): a v2 TECH draft re-flowed the same way (487 wc-w ≈ 1:1 words, 117 "." beats, H1 sections with `.` blank `.` separators) — tables collapse into staged bold questions, and the publish register goes full-พร.

   4a. **Slice a long draft into platform paths when it's long (or the user says "แบ้งเป็นหลาย path" / "แบ่งเป็นหลาย path").** A single 1500+ word long-form doesn't fit every feed. Produce a companion `YYYYMMDD-cnt-<slug>-paths.md` in `posts/` with one section per platform: **FB** = medium ~700 words (headingless "." format, same as a medium Type-A), **IG Carousel** = ~10 slides (hook → one idea each → CTA+sign-off), **X thread** = ~10 tweets numbered `N/` (hook first, hashtag core last), **Threads** = ~8 posts. Keep each platform's version self-contained (re-state the hook; don't say "as I said before"). File the paths file as a **separate Notion draft page** (companion to the main long-form — the long-form and its paths are two distinct Drafts pages, like a long-form + short version). This mirrors the Duck OS SSOT `/slice` and `/split` commands.
4b. **Scan the draft for foreign-script leakage before committing or pushing to Notion.** The local LLM drafting Thai occasionally emits Japanese-Kana / CJK / Korean tokens inside Thai sentences — caught twice in one session (a Japanese adverb in a draft body, a Chinese phrase in a STATE.md edit), and they pass every Thai-language check. **(190) Pricing/citation hygiene for pre-trial analyses (pair #49 publish):** pricing shrinks to what the decision needs (Free quota + Pro, dated "ตรวจเมื่อ 16 ตุลาคม 2026") + a re-check directive ("ควรตรวจหน้า Pricing อีกครั้งก่อนสมัคร") — deleted tiers (Growth/Enterprise) die with the fork they served; benchmark claims cite a checkable source line at the tail ("แหล่งข้อมูลสำหรับตรวจสอบ: wisprflow.ai") instead of the bare label "vendor claim" — traceability replaces adjective-hedging. **(191) Accuracy debt on precision-selling posts (pair #50 Benz r1, 2026-10-16):** a post whose selling point IS accuracy (a proven theorem, a benchmark, a spec) gets audited at that standard — "ใช้ความแม่นยำเป็นจุดขาย แต่คำอธิบายบางช่วงยังไม่แม่น". Draft-time audit list: (a) conditions COMPLETE at first statement (the secretary setup needs all of: random order / immediate irrevocable decision / no recall / rank-only information / known n / best-only goal — don't force an artificial count like "สี่ข้อ" that then omits two); (b) mechanism words verified against the actual math — "เก็บสถิติว่าดีหน้าตาเป็นยังไง" implies feature-learning, but the classical problem only yields RELATIVE RANK comparisons ("สร้างเกณฑ์เปรียบเทียบจากตัวเลือกที่ผ่านมา"); (c) edge cases stated: the policy can end selecting NOBODY (best-in-nobody's-reach case), and the failure mass is NOT one mode (missed-best ≠ picked-but-not-best); (d) rounded numbers labeled as approximations when a finite-n version has its own exact rule (37% of 100 ≈); (e) attribution RANGE — Gilbert & Mosteller 1966 = "งานสำคัญชิ้นหนึ่ง" of a continuously-developed field, never "ผู้พิสูจน์แรก" (Lindley 1961 predates); safe form: "ผลลัพธ์นี้เป็นส่วนหนึ่งของงานวิจัย X ที่พัฒนาต่อเนื่องมาหลายช่วง โดย A และ B ตีพิมพ์งานสำคัญในปี N".
**(192) The self-audit rule — a post warning against X must not commit X (pair #50 Blind Spot):** "37% ผูกกับโจทย์แคบ — แต่โครงสองช่วงไม่ผูก" smuggled an INTERPRETATION past the same gate the post holds the theorem to: the first clause is mathematics, the second is a life-application claim imported back from the theorem's domain. **(193) Killer-line single-cause check (extends EN #111) — multi-conditional results kill single-cause metaphors:** "มันคือราคาของโจทย์ที่ย้อนกลับไม่ได้" is catchy but names ONE condition as THE cause of a result produced by SEVERAL (random order + rank-only info + known n + best-only goal) — the critic's test: "ประโยคจำง่าย แต่ไม่แม่น". **(194) Condition-match examples get proximity status (pair #50):** offering a real-life case as "โจทย์ที่ตรงเงื่อนไข" (one-shot purchase offers) is itself an accuracy claim — real offers may not arrive in random order and the buyer may know true values (violating the rank-only condition). **(195) Reversible ≠ free (pair #50, system-post twin of rule 188):** the DuckOS lens for reversible decisions cuts BOTH ways — "ถ้าการตัดสินใจย้อนกลับได้ อย่าสร้างภาระการตัดสินใจให้ใหญ่เท่ากับเรื่องที่ย้อนกลับไม่ได้" (do not import irrevocable-game caution into reversible games), BUT "ย้อนกลับได้ ไม่ได้แปลว่าไม่มีต้นทุน" — experiments cost time/energy/money and can touch data or other people, so the operating question is "ต้นทุนของการทดลองอยู่ในขอบเขตที่รับไหวไหม"; and the experiment's evidence-status: "การทดลองไม่ได้มีไว้พิสูจน์ว่าเราเลือกถูก แต่มีไว้ให้ข้อมูลจริงสำหรับการตัดสินใจครั้งถัดไป" — trial = information-gathering, never correctness-proof. Decision principle left to the reader (gate-answered): ผ่านเกณฑ์ → ทดลองเล็ก → ดูผลจริง → ใช้ต่อหรือเปลี่ยน (not ดูให้มาก → เปรียบเทียบให้ครบ → เลือกให้ดีที่สุดตั้งแต่ครั้งแรก).
**(196) Condition-carrying rules get boundary sections (pair #51, 2026-10-18):** when a worked example carries a SHORT rule (กฎ 3 บรรทัด family), a one-line hedge ("อ่านเผิน ๆ อาจเหมือนคำสั่ง") does not scope it — the critique classes the rule as a universal command and BLOCKS publish ("ยังไม่ควรเผยแพร่โดยไม่แก้ตัวอย่างสามกฎ"). Draft-time gate: any rule stated in ≤1 line inside a worked example is a condition-carrying rule — either give it a boundary section in the same post, or keep it out of the worked example.
**(197) Rule-as-signal reframe (pair #51 gate):** when a critic's gate exposes that a rule word ("หยุด") reads as the DECISION while the author means the EVALUATION TRIGGER, the fix is the reframe grammar, not a definition footnote: "กฎไม่ได้เลือกคำตอบให้พร — มันช่วยเรียกกระบวนการประเมินขึ้นมา" + the speed/quality split "กฎลดการคิดซ้ำได้ โดยไม่จำเป็นต้องตัดการคิดทิ้ง". **(198) Compiled ≠ verified — fluency is not evidence (pair #51 §4):** the claim "ประโยคที่คอมไพล์แล้วมี...ความเด็ดขาด เพราะคนเขียนจ่ายค่าเรียนมาแล้วทั้งรอบ" died — decisiveness can be mere habituation ("ตัดสินใจผิดซ้ำจนคล่องได้เหมือนกัน"); relief after deciding ("ความโล่ง") is not proof the decision was best, and next-day costs (ร่างกายจ่ายต้นทุน) can contradict the in-the-moment feeling. **(199) Origin-agnostic ownership (pair #51 §5):** the borrowed-vs-compiled split, held hard, is over-compiled — borrowed lines can become real rules when tested on our cases, and self-extracted lines can be wrong ("ไม่ต้องปกป้องประโยคเพียงเพราะเราเป็นคนเขียนมัน"). **(200) Feedback-loop closure — the complete cycle ships in the critic's own form (pair #51 §6-7):** when a critique names both the defective cycle (สกัด → ใช้ตัดสินใจ, no check) and the complete one, the publish closes the loop VERBATIM as the asset line ("เจอเคสจริง → ตัดสินใจ → ดูผล → เห็นรูปแบบ → สกัดกฎ → ใช้ซ้ำ → ตรวจผลอีกครั้ง") + the keep/fix fork ("ถ้าใช้แล้วช่วยลดการคิดซ้ำ...เก็บไว้ / ถ้าใช้แล้วเริ่มพาไปผิดทาง...แก้ขอบเขตของกฎ"). Also `PATCH /v1/blocks/{page_id}/children` only APPENDS to the end of the page (no insert-position parameter) — to place a block near the top, include it in the full body replace instead of prepending via children. **Full-body swap (re-spine / critique rewrite) procedure, in order:** (1) try the documented path first — `PATCH /v1/pages/{id}/markdown` with `{"type":"replace_content","replace_content":{"new_str":...,"old_str":""}}` (same URL survives). (3) If even the append 400s (block-append not available on the pinned 2022-06-28 version), create a FRESH page via `POST /v1/pages` with the new content and ARCHIVE the old emptied page (`PATCH /v1/pages/{old_id}` `{"archived": true}`) — record the new page id in the draft header; do NOT leave the emptied old page as a stray `rewritten` entry.
