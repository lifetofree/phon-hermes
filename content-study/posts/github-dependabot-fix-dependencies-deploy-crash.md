# 🛠️ GitHub Dependabot ตัวช่วยดูแล Dependencies เวลา Deploy แล้วพัง

### 00: เมื่อ Vibe Coding เจอกับความจริงบน Production

กระแสการสั่งงานด้วยเสียงและข้อความเพื่อรันโค้ด หรือที่เรียกกันว่า Vibe Coding ในตอนนี้ พรเถียงไม่ได้เลยคับว่ามันช่วยประหยัดเวลาและสร้างต้นแบบแอปพลิเคชันขึ้นมาได้เร็วมาก

ในตอนที่รันสคริปต์บนระบบจำลอง (Local Machine) ทุกอย่างดูทำงานได้ดี ไม่มีข้อผิดพลาด Compiled ผ่านหมด 100%

แต่สภาวะที่โปรแกรมเมอร์มักจะเจอเหมือนกันเป็น Logs ซ้ำๆ คือ ทันทีที่กด Deploy สคริปต์แอปพลิเคชันตัวนั้นขึ้นสู่ระบบ Production ที่มีผู้ใช้งานจริง สิ่งที่ตามมากลับเป็นความพังทลาย:

- Deploy ปุ๊บ ระบบล่มพังปั๊บ: หน้าจอขึ้นรหัสเตือนภัย 500 Internal Server Error เพราะสภาพแวดล้อมบนคลาวด์ไม่รองรับคำสั่ง

- ระบบรักษาความปลอดภัยมีรอยรั่ว: มี Request แปลกปลอมแอบเจาะเข้ามาป่วนดาต้าเบสหลังบ้าน เพราะเปิดช่องโหว่ประตูระบบทิ้งไว้โดยไม่รู้ตัว

เมื่อตรวจสอบสาเหตุลึกซึ้งลงไป สิ่งที่ทำให้โค้ดระเบิดไม่ใช่เพราะ Logic หลักที่คุณป้อนให้ AI เขียนห่วย คับ แต่มันพังเพราะคุณไม่ได้เช็กว่าคลัง Library หรือ “Dependencies” ส่วนต่อขยายบางตัวที่ดึงมาใช้นั้น มันหมดอายุไปแล้ว (Deprecated) มีเวอร์ชันใหม่ออกมาแก้บั๊กแต่คุณลืมเปลี่ยน หรือมันมีช่องโหว่ Security สะสมอยู่ข้างใน คับ

ถ้าต้องมานั่งไล่เช็กเวอร์ชันและอ่าน Logs ของ Library ทีละตัวด้วยแรงคน มันดึงความจุสมองและเสียเวลามากคับ 

วันนี้พรเลยอยากแนะนำ “GitHub Dependabot” บอตระบบอัตโนมัติของ GitHub ที่จะมาทำหน้าที่เป็น รปภ. เฝ้าระวัง Repo แทนคุณตลอด 24 ชั่วโมง โดยที่คุณไม่ต้องจ่าย Cognitive Load ในการเฝ้าระวังเลยคับ

### 01: GitHub Dependabot คืออะไร?

สั้นๆ มันคือ Bot ผู้ดูแลความสะอาดของ Dependencies ที่ฝังตัวอยู่บนแพลตฟอร์ม GitHub คับ

หน้าที่ของมันคือคอยตรวจจับ Package Manifest (เช่นไฟล์ package.json หรือ go.mod) ใน Repository ของเรา
เมื่อไหร่ก็ตามที่ผู้พัฒนาภายนอกมีการออกเวอร์ชันอัปเดตใหม่ หรือทีมรักษาความปลอดภัยระดับโลกตรวจพบช่องโหว่ทางกฎความปลอดภัย (Vulnerability) ใน Library ตัวที่คุณรันอยู่

Dependabot จะไม่ได้แค่ส่งอีเมลแจ้งเตือนให้รำคาญ คับ แต่มันจะทำการสร้าง Pull Request (PR) ใหม่ขึ้นมาให้ใน Repo ของคุณโดยอัตโนมัติ
บอตจะทำการแก้เลขเวอร์ชันสคริปต์ในโค้ดให้เสร็จสรรพ พร้อมแนบ Diagnostic Logs รายละเอียดสรุปสิ่งที่เปลี่ยนไปในเวอร์ชันนั้นมาให้คุณอ่านแบบคลีนๆ

หน้าที่ของคุณมีเพียงแค่ตรวจดูความเสถียร สั่งรันคำสั่ง Test แล้วกดปุ่ม Merge สคริปต์ปลอดภัยนั้นเข้าสู่ฐานโค้ดหลักได้เลย

### 02: ข้อดีในการฝัง Dependabot ลงใน Workflow

- อัปเดต Package อัตโนมัติ (Automated Updates): ระบบจะคอยกวาดล้างและอัปเดตเวอร์ชันของ Library ให้ใหม่อยู่เสมอ ไม่ต้องคอยใช้แรงคนนั่งจำตารางเวลามาสั่งรันคำสั่งเช็กทีละตัว ลดโอกาสการเกิดปัญหา Dependencies เสื่อมสภาพ (Rot) คับ

- คัดกรองช่องโหว่ระดับสากล (Security Patches): บอตจะทำงานร่วมกับ GitHub Advisory Database ทันทีที่ Library ตัวไหนตรวจพบภัยเงียบ Security ระดับรุนแรง (CVE) มันจะยิงสคริปต์แก้ไข Patch เร่งด่วนเข้ามาให้ทันที ประตูหลังบ้านคุณจะถูกล็อกกลอนโดยอัตโนมัติ คับ

- ปลอดภัยต่อระบบ Production (Isolation Review): การแก้เลขเวอร์ชันทั้งหมดจะถูกกักขอบเขตประมวลผลอยู่แค่ในหน้าต่าง Pull Request เสมอ ทีมพัฒนาหรือตัวคุณเองสามารถเข้ามา Review โค้ด ตรวจเช็ก White Space ดูก่อนได้ โดยไม่มีผลกระทบด้านลบเชิงโครงสร้างต่อแอปพลิเคชันที่ออนไลน์อยู่

### 03: โพรโทคอลวิธีตั้งค่าใช้งาน (เลือกได้ 2 วิธีตาม Environment ทำงาน)

พรสรุปขั้นตอนวิธีเชื่อมต่อบอตตัวนี้เข้าคอร์โปรเจกต์งานของคุณแบบเข้าใจง่ายและขอบเขตชัดเจนไว้ให้ 2 รูปแบบ:

### รูปแบบที่ 1: ตั้งค่าผ่านหน้าต่าง GitHub UI (สำหรับ Environment ไม่เขียนโค้ด)

เป็นโพรโทคอลสั้นๆ ที่เปิดรันระบบผ่านหน้าจอควบคุมของ GitHub ได้โดยตรง

- เข้าไปที่หน้าต่าง Repository หลักบน GitHub ที่คุณต้องการตั้งค่าระบบป้องกัน

- คลิกที่แถบเมนูคอนฟิกด้านบน เลือก Settings

- ในแถบเมนูควบคุมซ้ายมือ เลื่อนลงมามองหาหมวด Security ค้นหาคำสั่ง Code security and analysis

- ส่องมองหาหัวข้อ Dependabot security updates และ Dependabot version updates จากนั้นกดคลิกปุ่ม Enable เพื่อเปิดระบบให้หุ่นยนต์เริ่มทำงานเปิดลูปจับตาดู Repo ทันที

### รูปแบบที่ 2: บังคับเขตแดนโครงสร้างด้วยไฟล์ dependabot.yml

หากโปรเจกต์ของคุณต้องการการคุมสเปก Configuration ที่ละเอียดและนิ่งขึ้น แนะนำให้สร้างไฟล์ระบบคอนฟิกฝังลงบอร์ดโปรเจกต์โดยตรง

- ที่ Root Directory ของโปรเจกต์งาน ให้สร้าง Folder ชื่อ .github

- ข้างในโฟลเดอร์นั้น ให้สร้างไฟล์ชื่อ dependabot.yml

- ก๊อปปี้และพิมพ์ Configuration Syntax ตัวนี้ฝังลงไปในไฟล์

YAML

	
		
			

version: 2updates:  # วางระบบสั่งบอตจับตาดู npm packages หลังบ้าน  - package-ecosystem: "npm"    directory: "/"    schedule:      interval: "weekly" # กำหนดวงรอบประมวลผลให้ตรวจเช็กทุกสัปดาห์  # วางระบบสั่งบอตตรวจสอบสถาปัตยกรรม Dockerfile  - package-ecosystem: "docker"    directory: "/"    schedule:      interval: "daily" # กำหนดวงรอบประมวลผลให้ตรวจเช็กทุกวัน
		
	

โครงสร้างคอนฟิกตัวนี้จะทำหน้าที่บอกระบบประมวลผลของบอตชัดเจน คับ ว่าให้เน้นดูเฉพาะ Package หลังบ้านที่เราดึงมาใช้งานจริงตาม Directory และคุมความถี่ในการยิง PR (Interval) ไม่ให้รบกวนหน้าต่าง Workflow ทำงานประจำวัน

### #สรุปแบบวิศวกรเป็ด

ในการทำซอฟต์แวร์หรือ Coding ยุคนี้ การพึ่งพาความจุความจำของแรงมนุษย์มานั่งไล่เฝ้าระวัง Dependencies ทีละบรรทัด คือกลไกการทำงานที่มีความเสี่ยงและขาดเสถียรภาพที่สุด คับ

ถ้าคุณยังไม่เคยติดตั้งระบบ Dependabot คอยสแกนคลังโปรเจกต์หลังบ้าน บอกเลยว่าระบบของคุณกำลังรันงานอยู่บนสภาพแวดล้อมที่เสี่ยงพังได้ตลอดเวลา คับ

กลับมาดูแลรักษาความสะอาดของ Environment ย้ายงานที่ซ้ำซากน่าปวดหัวไปฝากไว้ให้ระบบอัตโนมัติมันรันตรวจสอบแทน 24 ชั่วโมงซะ คับ แล้วนำเวลาและทรัพยากรแบตเตอรี่ในหัวของคุณ ไปโฟกัสกับการออกแบบ Logical โค้ดหลักให้ส่งมอบ Value ทรงพลังออกมาแบบไร้รอยต่อดีกว่า
