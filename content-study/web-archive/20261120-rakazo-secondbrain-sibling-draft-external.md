### โครงสร้างของฐานความรู้เราครบทุกเล่ม แต่เนื้อหาอยู่แค่ 41 เล่ม — นับจริง 20 พ.ย. 2026
.
## วันนี้เรานับฐานตัวเอง แล้วเจอว่าตัวเลขแรกมันหลอกเรา
ฐานหนังสือของเรามี 251 เล่ม แท็กที่ใช้งานจริง 76 แท็ก ผูกกัน 532 ครั้ง และในหน้าเล่มแต่ละเล่มมีตารางบทแยกอีก 253 ตาราง ตัวเลขพวกนี้ทำให้ฐานดูเหมือนคลังของใหญ่ที่มีของครบ
แต่พอนับต่อว่าตารางบทใดมีบทอยู่จริงบ้าง ผลที่ได้คือมีแค่ 42 ตารางจาก 253 ที่มีแถว รวมทั้งหมด 644 แถว อีก 211 ตารางว่างสนิท นับเป็นรายเล่ม มี 41 เล่มจาก 251 ที่มีบทอยู่จริง
ตัวเลข 251 กับ 253 คือจำนวนโครงสร้าง ส่วน 41 กับ 644 คือจำนวนของจริง ถ้าเราดูแค่ตัวแรก เราจะเข้าใจผิดว่าเราเก็บได้เยอะ
จุดที่ทำให้เราหยุดคือระหว่างนับเอง มี 4 ตารางที่ query ไม่ผ่าน โดน Notion ตอบ 429 กลับมา แล้วสคริปต์ก็ข้ามไปเงียบ ๆ ตัวเลขแรกที่ได้จึงเป็น 637 ไม่ใช่ 644 — ไม่ใช่เพราะข้อมูลหาย แต่เพราะทางที่เราไปหยิบมันกลับมามีเพดาน และเพดานนั้นไม่ได้แปลงเป็นคำว่าไม่ครบในหัวเรา มันแปลงเป็นตัวเลขที่ดูเหมือนจริง
.
## ชั้นที่ควรดึงข้อมูลกลับมา รั่วตรงจุดที่เงียบที่สุด
พอเปิดสคริปต์ที่ดูแลฐานหนังสือ ก็เห็นว่ามันอ่านข้อมูลของตัวเองไม่ครบ จุดแรกคือฟังก์ชันที่แปลงค่าจาก Notion ให้เป็นข้อความ มันอ่านได้แค่ชนิด title ชนิด rich text และชนิด select พอคอลัมน์แท็กเปลี่ยนเป็นชนิด multi select ค่าที่ได้ก็กลายเป็นค่าว่าง — แท็ก 532 ครั้งที่ผูกไว้ในฐาน ไม่เคยถูกดึงกลับไปไว้ที่ไหนเลย
จุดที่สองคือการเลือกตารางบท มันเลือกจากชื่อ โดยเอาตารางที่ชื่อมีคำว่า chapter เท่านั้น ตารางที่หลุดเงื่อนไขมีอยู่จริง เช่นตารางที่ชื่อว่า New database ซึ่งมีบทอยู่ 7 แถว — ตารางนั้นไม่เคยถูกมองเห็น
จุดที่สามไม่ใช่บั๊ก แต่เป็นความไม่เป็นเนื้อเดียวกันของข้อมูล คอลัมน์ core message ถูกสะกดไว้สามแบบ และตารางที่มีบทจริง 42 ตาราง ยังมี 12 ตารางที่ไม่มีคอลัมน์นี้เลย สคริปต์จับค่าจากชื่อที่มีคำว่า core จึงได้ค่าที่ไม่ครบในหลายตาราง
สามจุดนี้เรียงกันได้เป็นเรื่องเดียว — โครงสร้างอยู่ครบ แต่ชั้นที่ควรดึงมันกลับมามีรอยรั่ว และผลที่ออกมาดูเป็นเรียบร้อยทั้งที่ไม่ครบ
.
## Notion เองก็มีเพดานที่วัดได้ และเอกสารเขียนไว้ตรง ๆ
ข้อจำกัดจากเอกสารทางการของ Notion เป็นตัวเลข ไม่ต้องเดา — ต่อหนึ่ง connection ดึงได้ 180 request ต่อนาที แผน Business กับ Enterprise ได้ 600 ต่อนาที และการ query data source มีลิมิตแยกราว 3 request ต่อวินาที มีงบร่วมกันทั้ง workspace ที่ทุก connection ต้องแชร์ เกินเมื่อไรได้ 429 พร้อม Retry-After กลับมา
ฝั่งขนาด ฐานฟรีที่มีสมาชิกมากกว่าหนึ่งคนมีเพดานพัน blocks ตลอดอายุการใช้งาน และการลบไม่คืนโควตา เขียนเกินได้ 403 หลังเลยรอบผ่อนผันสามวัน ส่วนฐานเสียเงินกับฐานฟรีแบบสมาชิกคนเดียวไม่ติดเพดานนี้
ความสัมพันธ์ระหว่างฐานเป็น one-way โดย default ต้องไปเปิดที่ฐานปลายทางเองถึงจะย้อนกลับได้ และ Search API ค้นด้วยชื่ออย่างเดียว เอกสารเตือนตรง ๆ ว่าอย่าเอาผลลัพธ์มาใช้เป็นรายการของทั้งคลัง ถ้าเรามองฐานทั้งหมดผ่าน search เรากำลังดูฐานที่ไม่ครบ
แต่ของที่ทำให้เรายังไม่ตัดสินใจว่า Notion เป็นคำตอบ คือ webhook มีอยู่จริงและเป็น realtime ตรวจได้ด้วย verification token กับ HMAC-SHA256 แปลว่า sync สองทางทำได้ เพียงแต่ต้องเขียนเองและดูแลเอง ส่วน MCP ไม่ได้ลากความจำของ client อื่นเข้ามาให้ เอกสารระบุตรง ๆ ว่าการต่อ MCP ไม่ได้ import ประวัติแชทของ client อื่นมาให้โดยอัตโนมัติ ความจำข้าม agent จึงต้องอยู่ใน Notion จริง ๆ
.
## second brain ที่ใช้ได้จริง วัดที่การดึงกลับมา ไม่ใช่ที่จำนวนที่เก็บ
กรอบที่ใช้ได้ที่สุดของ Tiago Forte คือ CODE สี่ขั้น คือ Capture แล้ว Organize แล้ว Distill แล้ว Express และ PARA ที่บอกว่าให้จัดตามความพร้อมที่จะถูกใช้ ไม่ใช่ตามหมวดหมู่ เพราะการจัดตามหมวดหมู่ทำให้เกิด silo ที่หลุดไม่ได้
หลักการสองข้อที่ตรงกับเคสของเรามากที่สุดคือ Keep Your Ideas Moving กับ You Only Know What You Make ข้อแรกคือระบบที่ต้องสมบูรณ์แบบถึงจะใช้ได้นั้นพัง ข้อที่สองคือสิ่งที่เราไม่เคยทำออกมา เราจะไม่รู้ว่าเรารู้จริง ส่วน Matuschak เขียนว่าการจดโน้ตที่ดีกว่าไม่ใช่ประเด็น ประเด็นคือการคิดที่ดีกว่า โน้ตที่ดีควร atomic ตั้งอยู่บนแนวคิด เชื่อมกันแน่น และเขียนไว้เพื่อตัวเอง
ถ้าจะตัดให้สั้น ฐานความรู้ที่ใช้ได้จริงต้องมีสามชั้น คือโครงสร้าง เรื่องคนใช้ และเรื่อง loop ที่ดึงข้อมูลกลับมา ฐานของเรามีโครงสร้างแล้วแต่ยังไม่ตรงกันในหลายตาราง มีคนใช้อยู่จริงทั้งทีมบอทและพร และกำลังมี loop วิ่งอยู่จริง — agent อ่านฐานความรู้ แล้วสรุปเป็นโน้ตใหม่ แล้วเขียนกลับเข้าไป ให้คน review แล้วรอบถัดไปก็เริ่มจากโน้ตที่เพิ่งเขียน นั่นคือ Distill แบบ opportunistic ของ Forte — แตะโน้ตทีไหน เพิ่มมูลค่าให้มันทีละนิด
เกณฑ์วัดที่ไม่ต้องเชื่อใครคือแบบนี้ — เปิดฐานแล้วหาข้อมูลที่มีอยู่แล้ว ต้องเปิดกี่หน้าถึงเจอ ถ้าต้องไล่หาห้าหน้าเพื่อได้สิ่งที่อยู่ในฐานแล้ว ฐานนั้นยังไม่ได้ทำงานเหมือนสมองที่ใช้ได้
.
## คำถามที่เรายังไม่ตอบ
loop ที่ดึงข้อมูลกลับมากำลังเกิดอยู่จริง โน้ตความรู้ที่ทีมวิจัยเขียนไว้เมื่อวันที่ 20 พ.ย. คือต้นทางของบทนี้เลย แต่เรายังไม่ได้วัดว่ารอบการดึงกลับมาของเราใช้เวลานานแค่ไหน
คำถามที่อยากเก็บไว้ก่อนในบทนี้เลยคือข้อนี้ — ถ้าวันหนึ่งเราต้องเปิดฐานเพื่อหาข้อมูลที่มีอยู่แล้ว เราจะนับมันเป็นรอบของการดึงกลับมา หรือนับเป็นรอบของการหา เพราะถ้าวันไหนสองอย่างนี้แยกไม่ออก แปลว่าฐานของเรายังเป็นที่เก็บ ยังไม่ใช่สมองที่ใช้ได้
.

สาระของเรื่อง — second brain ที่ใช้ได้จริงไม่ได้วัดที่จำนวนที่เก็บไว้ แต่วัดที่ความเร็วในการดึงสิ่งที่ต้องใช้กลับมา และฐานของเราตอนนี้มี 251 เล่ม 76 แท็ก 253 ตารางบท แต่บทที่มีอยู่จริงอยู่แค่ 41 เล่ม
ที่เป็ดมอง — ข้อมูลไม่ได้หาย ทางที่ไปหยิบมันกลับมาหาย คอลัมน์แท็กแบบ multi select ที่สคริปต์อ่านไม่รู้จัก ตารางที่ชื่อไม่ตรงเงื่อนไข และคอลัมน์ core message ที่สะกดไว้สามแบบ ทำให้ผลที่ออกมาดูเป็นเรียบร้อยทั้งที่ไม่ครบ
