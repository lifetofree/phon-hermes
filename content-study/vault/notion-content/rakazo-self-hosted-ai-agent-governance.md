บันทึก 3 วันแรกบน Docker เมื่อปัญหาไม่ได้อยู่ที่โมเดล แต่อยู่ที่สิทธิ์และกระบวนการ
การติดตั้ง AI Agent ให้ทำงานบนเครื่องของเราเอง อาจดูเหมือนเป็นเรื่องของการเตรียม Docker, ดาวน์โหลด Image และสั่งให้ Container ทำงาน
แต่เมื่อเริ่มให้ Agent แตะไฟล์จริง ทำงานกับ Repository จริง และส่งงานกลับเข้าระบบจริง คำถามจะเปลี่ยนไปทันที
ไม่ใช่แค่ว่า มันทำงานได้หรือยัง
แต่เป็นว่า เราวางสิทธิ์และกระบวนการไว้ดีพอที่จะให้มันทำงานต่อได้อย่างน่าเชื่อถือหรือไม่
นี่คือบันทึก 3 วันแรกของการทดลองใช้ Rakazo บนเครื่องตัวเอง
Rakazo คืออะไร
จากคำอธิบายใน README, Rakazo เป็นระบบ AI Team แบบ Open Source ที่สามารถติดตั้งและใช้งานบนเครื่องของเราเองได้
แนวคิดคือให้ AI ทำงานร่วมกันเป็นทีม โดยมีองค์ประกอบอย่าง Memory, Routines, Apps และ Computer รวมถึงสามารถเลือกใช้โมเดลที่ต้องการได้
สิ่งที่น่าสนใจจึงไม่ใช่แค่การเปิดหน้าต่าง Chat แล้วคุยกับ AI แต่เป็นการเตรียมสภาพแวดล้อมให้ Agent สามารถรับงานและลงมือทำงานได้จริง
โครงสร้างที่ติดตั้ง
การติดตั้งครั้งนี้ใช้ Docker Compose โดยมี Container หลัก 5 ตัว ได้แก่
Container หลักทั้ง 5 ตัวใช้ Image เดียวกัน และมี Bot Computer แยกออกมาอีก 1 Container
รวมทั้งหมด 6 Containers
ไฟล์ที่ใช้ในการติดตั้งมีทั้ง docker-compose.images.yml, Script สำหรับ Pull Image จาก ghcr.io และ Script สำหรับจำกัด Egress หรือการเชื่อมต่อออกไปยังเครือข่ายภายนอก
มี Image หลัก 2 ชุด ขนาดรวมประมาณ 5.2 GB
หลังสั่ง Compose Up เวลา 15:52 น. วันที่ 16 พฤศจิกายน 2026 ทั้ง 6 Containers เริ่มทำงานได้
สามารถเข้าใช้งานผ่าน localhost:5173 และเข้าผ่าน Tailscale Domain ได้ โดยจำกัดการเข้าถึงไว้กับอุปกรณ์ในเครือข่ายส่วนตัว
สองวันหลังจากติดตั้ง บันทึกระบุว่า Container หลัก 4 ตัวที่ตรวจสอบยังอยู่ในสถานะ Healthy
ตรงนี้มีรายละเอียดที่ควรแยกให้ชัดในการตรวจสอบรอบถัดไปว่าอีก 2 Containers มีสถานะอย่างไร เพราะการที่ระบบเริ่มทำงานได้ครบ ไม่ได้แปลว่าทุกส่วนยังทำงานปกติในระยะยาว
ให้ Agent ทำงานกับไฟล์จริง
ส่วนที่น่าสนใจคือการเชื่อมต่อพื้นที่ทำงานของ Agent เข้ากับไฟล์บนเครื่อง
การทดลองนี้มีการ Mount โฟลเดอร์เข้าไปใน Sandbox สองส่วน
แนวทางนี้ทำให้ Agent เข้าถึงข้อมูลจริงได้ โดยยังแยกพื้นที่สำหรับส่งต่องานออกจาก Repository หลัก
อีกส่วนหนึ่งคือการเชื่อมต่อกับ llama-server ที่ทำงานอยู่ในเครื่องผ่าน Port 8080 ทำให้การทดลองนี้ใช้โมเดลที่รันในเครื่องได้ โดยไม่ต้องเรียก External Model API สำหรับงานที่ทดลองครั้งนี้
อย่างไรก็ตาม คำว่าไม่เสียค่า API ไม่ได้หมายความว่าการรันไม่มีต้นทุนเลย เพราะยังมีค่าเครื่อง ไฟฟ้า และทรัพยากรที่ใช้ประมวลผลอยู่
งานแรก: Sync YouTube Clip Library จาก Notion
หลังติดตั้งระบบ งานแรกที่ให้ Bot ทดลองทำคือ Sync ข้อมูล YouTube Clip Library จาก Notion เข้ามาใน Repository ของตัวเอง
เป้าหมายคือให้ Bot สร้างไฟล์สรุป Clip จำนวน 3 ไฟล์ และส่งงานกลับเข้าระบบผ่าน Git
วันที่ 16 พฤศจิกายน เวลา 23:05 น. Bot ทำงานสร้างไฟล์ทั้ง 3 รายการเสร็จ และพยายาม Push Branch ชื่อ rakazo/youtube-library
แต่ได้รับข้อผิดพลาด 403 Forbidden
เวลา 23:33 น. มีการเขียน Token ลงใน Credential File ภายหลัง แต่จากลำดับเวลาที่บันทึกไว้ ยังไม่ควรสรุปว่า Token นี้เป็น Credential ที่ใช้ในการ Push ครั้งแรก หรือเป็นสาเหตุที่ทำให้การ Push ภายหลังสำเร็จ
วันที่ 18 พฤศจิกายน งานถูกปิดด้วยการ Cherry-pick ไฟล์ทั้ง 3 รายการกลับเข้า Main Branch
ได้ Commit 3e6f0eb รวม 225 บรรทัด
ผลลัพธ์คือไฟล์งานกลับเข้ามาอยู่ใน Repository หลักได้ แต่เหตุการณ์นี้เปิดให้เห็นปัญหาสำคัญกว่าการสร้างไฟล์สำเร็จหรือไม่สำเร็จ
Agent ทำงานเสร็จ ไม่ได้แปลว่ากระบวนการส่งมอบงานเสร็จด้วย
ปัญหาที่เจอจริง ไม่ได้อยู่ที่โมเดล
จากการทดลอง 3 วัน มีข้อสังเกตที่สำคัญอยู่หลายจุด
1. การจัดการ Error ยังไม่สมบูรณ์
เมื่อ Push ไม่สำเร็จ ระบบไม่มี Retry Mechanism ที่ทำให้ Agent กลับมาลองใหม่หลัง Credential พร้อมใช้งาน
ผลคือแม้จะมีการแก้ไข Credential ภายหลัง แต่สถานะของงานยังค้างอยู่กับข้อผิดพลาดเดิม
นี่เป็นช่องว่างระหว่างการทำงานสำเร็จในระดับ Task กับการทำงานสำเร็จในระดับ Process
2. สิทธิ์ของ Token กว้างเกินไป
Token ที่ใช้ควรมีสิทธิ์เท่าที่จำเป็น และจำกัดขอบเขตให้เหมาะกับ Repository ที่ Agent ต้องทำงานด้วย
การให้ Token ที่มีสิทธิ์กว้างเกินความจำเป็น เพิ่มความเสี่ยงโดยไม่ได้เพิ่มประโยชน์ให้กับงานโดยตรง
แนวทางที่ควรทำต่อคือใช้ Fine-grained Token และจำกัดสิทธิ์เฉพาะ Repository และการกระทำที่จำเป็น
3. Egress ยังไม่ได้ถูกล็อก
แม้จะมี Script สำหรับจำกัด Egress เตรียมไว้แล้ว แต่ในการทดลองครั้งนี้ยังไม่ได้รัน Script ดังกล่าว
หมายความว่า Sandbox ยังสามารถเชื่อมต่อ Internet ได้
การติดตั้งระบบไว้บนเครื่องตัวเองจึงไม่ได้แปลว่าเราควบคุมการเชื่อมต่อออกไปได้ทั้งหมดโดยอัตโนมัติ
เรื่องนี้ต้องแยกให้ออกระหว่าง Self-hosted กับ Controlled Environment เพราะเป็นคนละเรื่องกัน
4. ทรัพยากรของแต่ละ Bot
ในการตั้งค่าครั้งนี้มีการกำหนด RAM Limit ให้แต่ละ Bot ที่ 2 GB
หากต้องทำงานที่ใช้ทรัพยากรมากขึ้น อาจจำเป็นต้องปรับ Limit ให้เหมาะกับลักษณะงาน
แต่ไม่ควรเพิ่มทรัพยากรไปก่อนโดยไม่มีข้อมูล เพราะปัญหาอาจไม่ได้อยู่ที่ RAM แต่อยู่ที่ขั้นตอนหรือการออกแบบงานก็ได้
สิ่งที่ได้จาก 3 วันแรก
การติดตั้ง Rakazo ครั้งนี้แสดงให้เห็นว่าเราสามารถเตรียมสภาพแวดล้อมให้ AI Agent ทำงานบนเครื่องตัวเองได้
สามารถเปิดระบบผ่าน Docker, เชื่อมต่อกับโมเดลที่รันในเครื่อง และให้ Bot สร้างไฟล์จากข้อมูลจริงได้
แต่เมื่อ Agent ต้องทำงานต่อเนื่องผ่านหลายขั้นตอน ปัญหาที่ปรากฏกลับไม่ใช่ความสามารถของโมเดลเพียงอย่างเดียว
มันเกี่ยวข้องกับเรื่องที่ดูธรรมดากว่า เช่น
สิ่งเหล่านี้เป็นส่วนหนึ่งของระบบที่ทำให้ Agent ทำงานได้อย่างน่าเชื่อถือ
ขั้นต่อไปไม่ใช่เพิ่มจำนวน Bot
จากสิ่งที่พบ ลำดับงานต่อไปควรเป็นการจัดการจุดเสี่ยงที่มีอยู่ก่อน
โดยเฉพาะเรื่อง Git Permission และเส้นทางไฟล์ ยังต้องตรวจสอบให้ชัดว่า Repository ที่ Mount แบบ Read-only เชื่อมโยงกับขั้นตอนการสร้าง Branch และ Push อย่างไร
เพราะถ้าเราไม่รู้ว่า Agent เขียนไฟล์ตรงไหน ใช้ Credential อะไร และใครเป็นผู้ส่งงานกลับเข้า Repository เราก็ยังอธิบายกระบวนการทำงานทั้งหมดไม่ได้
การเพิ่ม Bot หรือเพิ่มงานในตอนนี้จึงยังไม่ใช่สิ่งที่ควรรีบทำ
ระบบที่รันได้ คือจุดเริ่มต้น แต่ระบบที่ทำงานต่อได้เมื่อเกิดข้อผิดพลาดต่างหาก ที่ทำให้เราเริ่มไว้วางใจมันได้
#สรุปแบบวิศวกรเป็ด
การติดตั้ง AI Agent บนเครื่องตัวเองอาจเป็นเรื่องที่ทำให้เห็นผลได้ภายในไม่กี่ชั่วโมง
แต่การทำให้มันทำงานกับไฟล์จริง สิทธิ์จริง และระบบจริงได้อย่างน่าเชื่อถือ เป็นอีกโจทย์หนึ่ง
อย่าเพิ่งวัดความสำเร็จจากจำนวนงานที่ Agent ทำเสร็จ
ลองวัดจากวันที่มันทำงานผิดพลาด แล้วระบบยังสามารถตรวจพบ แก้ไข และส่งงานกลับมาได้อย่างถูกต้อง
เพราะสุดท้ายแล้ว เราไม่ได้ต้องการแค่ AI ที่ทำงานเก่ง
เราต้องการระบบที่ไม่ต้องให้เจ้าของคอยตามแก้ทุกครั้งที่มีอะไรผิดพลาด
