## 0. ข้อสรุปสั้น (สำคัญที่สุด)

คู่มือเล่มนี้ **ไม่ใช่ e-book** และ **ไม่ใช่บทความ** — เป็น **"คู่มือทำงาน" (technical manual)**: เอกสารที่คนอ่านแล้วต้อง **ทำตามได้จริงจนจบ** และต้องแก้ปัญหาเองได้

ดังนั้นใน project ถัดไป ให้เลือก "manual" เมื่อ:
- ผู้อ่านต้องทำ action ได้จริง (ติดตั้ง/ตั้งค่า/ใช้งาน)
- มีคำสั่ง copy-paste และผลลัพธ์ที่ต้องได้
- มีจุดที่พังบ่อย → ต้องมีบทแก้ปัญหา
- ผู้อ่านคือ "คนที่จะทำ" ไม่ใช่ "คนที่จะอ่านคิด"

| ต้องการ | ใช้ format ไหน |
|---|---|
| สอนคิด/ระบบชีวิต/เรื่องเล่า | **e-book DuckOS format** → `shared/ebook-format-reference-duckos-v03.md` (Poppins + Prompt + Georgia, 20 หน้า, สไตล์ adduckivity, เสียง "พร") |
| สอนลงมือทำ/ติดตั้ง/ใช้งานเครื่องมือ | **Manual format** → ไฟล์นี้ (IBM Plex Sans Thai + IBM Plex Mono, 45 หน้า, เสียง "คุณ") |
| โพสต์ลง FB/เว็บ | **skill adduck-writer** (v1 กับ v2 tech form) |

> ⚠️ สอง format นี้ **ต่างกันจริง** — คนละฟอนต์ คนละน้ำเสียง คนละความยาว ห้ามนำสไตล์ของเล่มหนึ่งไปใช้กับอีกเล่มโดยไม่ตั้งใจ

## 1. โครงร่างเล่ม (Skeleton)

```
หน้า 1   ปก (cover)
หน้า 2   สารบัญ (แบ่งเป็น "ส่วนที่หนึ่ง/สอง/..." + ภาคผนวก)
หน้า 3   ปฐมบท / PREFACE — ทำไม, เหมาะกับใคร, ไม่ครอบคลุมอะไร, เป้าหมายของเล่ม
หน้า 4+  เนื้อหา 11 บท แบ่ง 4 ส่วน (Part 1-4)
ท้ายเล่ม ภาคผนวก A (cheat sheet) · ภาคผนวก B (ตารางตัวแปร) · ท้ายเล่ม (COLOPHON: แหล่งอ้างอิง + สัญญาอนุญาต + ข้อจำกัดความรับผิด)
```

| ส่วน | หัวข้อ | บท | หน้า |
|---|---|---|---|
| ปฐมบท | ก่อนเริ่มอ่าน — ทำไมต้องทำแบบนี้ | — | 3 |
| ส่วนที่หนึ่ง | เข้าใจก่อนลงมือ | 01–02 | 4–13 |
| ส่วนที่สอง | ติดตั้งและเปิดใช้งาน | 03–05 | 14–25 |
| ส่วนที่สาม | ให้มันทำงานจริง | 06–08 | 26–34 |

## 4. กฎการเขียน (Writing Rules) — จากต้นแบบจริง

### 4.1 เสียงและมุมมอง
- ใช้ **"คุณ"** ทั้งเล่ม (ต่างจาก e-book ที่ใช้ "พร")
- ประธานคือผู้อ่าน ไม่ใช่ผู้เขียน: "คุณจะได้…", "ถ้าคุณ…" ไม่ใช่ "เราได้…"
- ไม่มีคำประจำปี ประจำตัว ประจำทีม ไม่มีมุก ไม่มีอีโมจิแปลงคำพูด
- ไม่เหมือนการโฆษณา: ห้าม "สุดเพอร์!", "สุดคุ้ม!", "ไม่ต้องเชื่อก็ได้ว่า…"

### 4.2 หลักการเนื้อหา (5 ข้อที่ทำให้เล่มนี้ดี)
1. **บอกเหตุผลของคำสั่งทุกครั้ง** — ไม่ใช่แค่รัน ต้องบอกว่าทำไม เช่น "`-fsSLO` จะทำให้ curl ล้มเหลว loudly ถ้าดาวน์โหลดไม่สำเร็จ แทนที่จะเขียนไฟล์เปล่า"
2. **ให้ผลลัพธ์ที่ต้องได้ + เวลาที่ใช้** — "ใช้เวลา 10–25 นาที", "ผลที่ควรได้: บรรทัดแรกขึ้นต้นด้วย Docker version 26"
3. **บอกทางเลือกที่ไม่ต้องจ่ายเพิ่ม** — เป็นคุณค่าเพิ่มที่คู่มือทั่วไปไม่มี
4. **ซื่อสัญญาณความล้มเหลวก่อนเจอปัญหา** — "ถ้าเปิดหน้าเว็บได้ปกติแต่บอทเงียบ ปัญหาอยู่ที่โมเดล" (แยกชั้นที่มีปัญหา)
5. **ยอมรับข้อจำกัดตรง ๆ** — มีกล่อง "สิ่งที่ควรรู้ก่อนตัดสินใจ" (beta, ข้อมูลไม่มี backup) และหัวข้อ "หนังสือเล่มนี้ไม่ครอบคลุมอะไร"

### 4.3 โครงของบท (ทุกบท ใช้ซ้ำได้)
```
หัวบท (kicker + ชื่อ + lead)
→ ภาพรวบ/บริบทที่ต้องรู้ก่อน (ตารางหรือกล่อง)
→ ขั้นที่ 1..N (คำสั่ง + กล่องโค้ด + ผลที่ควรได้ + callout ที่จำเป็น)
→ ตรวจว่าสำเร็จ (เส้นเช็กสั้น)
→ (ถ้าเป็นบทหลัก) แผนต่อไป / สิ่งที่ควรรู้
```

### 4.4 ปฐมบทต้องมี 4 ส่วนนี้เสมอ
1. ทำไม (ปัญหาที่เล่มนี้แก้)
2. **หนังสือเล่มนี้เหมาะกับใคร** (กระจุก 3–4 ข้อ)
3. **สิ่งที่ควรรู้ก่อนตัดสินใจ** (ข้อจำกัด/ความเสี่ยง — ต้องมี)
4. **หนังสือเล่มนี้ไม่ครอบคลุมอะไร** (ขอบเขต)
5. เป้าหมายของเล่มนี้ (ประโยคเดียว มีตัวเลข — "ภายในหนึ่งชั่วโมง…")

### 4.5 ท้ายเล่ม (COLOPHON) ต้องมี
- แหล่งอ้างอิง (ไฟล์/เอกสารต้นทางที่คัดลอกมา — บอกตรง ๆ ว่าคัดจากต้นแบบ)
- สัญญาอนุญาตของสินค้าที่อธิบาย
- ข้อจำกัดความรับผิด (เวอร์ชัน/วันที่ที่เขียน → เอกสารอาจเปลี่ยน)

## 5. สายการผลิต (Production Pipeline)

ต้นแบบยืนยันจาก metadata: **HTML → พิมพ์เป็น PDF ด้วย Chrome (HeadlessChrome 157 / Skia m157)**

```
1. เขียน HTML 1 ไฟล์ = 1 หน้า A4 เรียงต่อกัน (class .sheet ต่อหน้า)
2. CSS: @page { size: A4; margin: 0 } + .sheet { height: 297mm; page-break-after: always }
3. ซ่อนองค์ประกอบจอตอนพิมพ์ (ปุ่ม Print, badge) ด้วย @media print
4. ไม่พึ่ง JavaScript ในผลลัพธ์
5. Chrome: window.print() → Save as PDF  (หรือ headless --print-to-pdf)
6. ตรวจ: ฟอนต์ embedded? เลขหน้าตรง? ไม่มีหน้าโล่ง/หน้าซ้าย?
```

ข้อควรระวังจากต้นแบบ:
- มีฟอนต์ **Type 3** ปนอยู่ 2 ตัวใน PDF (จากการ render ตัวอักษรไทยบางส่วน) → เป็นสัญญาณว่าไม่ควร embed ฟอนต์แบบ subset ที่ผิดวิธี; ให้ใช้ฟอนต์จาก Google Fonts แล้ว print ผ่านเบราว์เซอร์ที่โหลดฟอนต์ครบ
- ต้องทำ **content check ทุกครั้ง**: เลขหน้า, สารบัญ-หน้า, คำสั่งยังถูกต้องกับของจริง
