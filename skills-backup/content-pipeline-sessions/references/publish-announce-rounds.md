# Publish/announce round plumbing (lesson bodies relocated from SKILL.md to stay under the size cap)

## 56. Fresh-publish announce round: owner posts the live WP URL of a post we hold as a paste archive

The owner announcing a live WP URL for a post already analyzed from a paste is a closing round, not a new analysis: (1) run the WP sync script (`python3 ~/.hermes/scripts/sync_wp_posts.py`) — it archives the new post, appends index.json, and commits+pushes itself; the announce CONFIRMS new posts exist, so a silent run means the sync broke, never "nothing new" — and a NON-EMPTY run can still be incomplete: the wp-json collection endpoint can serve a stale cached list, so assert the announced post's own slug is in the run's archived set before closing; if it is missing, re-run once (a fresh fetch) and reconcile the two runs' counts instead of accepting "N new posts" as complete; (2) normalized-diff the fresh WP archive against the paste archive — expect ONLY markdown-stripping deltas (heading/bold markers stripped, title-prop vs H1 shape); any other line delta is a real WP-side edit to record, never to fix; (3) the WP render may carry an owner-added hashtag tail beyond the default trio — the as-fits tags rule already covers this, log the tail in the pair's index note instead of treating it as a deviation; (4) bind the live URL as `wp_link` on the PAIR's index entry (keep the sync script's own archive entry separate — one describes the pair loop, the other the WP snapshot) and commit. The pair then closes with both surfaces linked: Notion production page + WP live. Variant — announce with NO paste archive and NO pair (owner-authored off-pipeline): step (1) still runs, steps (2)-(4) are skipped (nothing to diff or bind), the round closes with a provenance note on the sync's index entry (owner-authored, analyze-only per lesson 11), and the Content DB stays untouched — never create a Drafts page for it.

## 58. Publish-first intake — the production page may already exist owner-built in the Content DB

When the owner pastes a publish version that passed DNA elsewhere ("publish version ที่ผ่านการตรวจแล้ว"), do NOT create a Drafts page: search BOTH DBs by title first. The Content DB's title property is `Headline`, the Drafts DB's is `Name` — a workspace-search hit list must read EACH hit's title-TYPE property to test the match (a loop reading only `Name` sees the Content DB hits as empty strings and can conclude "no existing page" against evidence), and the same asymmetry bites database QUERY filters: a title-contains filter names the property literally, so filtering the Content DB on `Name` returns ZERO results with no error — run the existence filter against each DB's OWN title property (Drafts → Name, Content → Headline), never one shared filter for both. If the owner already built the production page (full body blocks, an image, a `====` separator, Status 🟧 Visualizing, Platform multi-select WP/FB/TH/IG), the round is analyze-only: archive verbatim → fact-check across ≥3 outlets → measure → propose skill folds in chat and wait for approval → index-entry link (`link` + `notion_page_id`), and the production page stays UNTOUCHED — no PATCH, no Status flip, no rebuild. The agent's Status vocabulary (`draft`/`published`) is a Drafts-DB instrument; emoji-stage statuses on the Content DB are the owner's production pipeline and are read, never written. When the owner later announces the WP live URL, close per lesson 56 (sync script → markdown-strip diff → bind `wp_link` on the pair entry).
