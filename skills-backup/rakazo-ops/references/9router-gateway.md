# 9Router LLM gateway (self-hosted, server port 20128)

Self-hosted OpenAI-compatible gateway (decolua/9router) that fronts the fleet's model chain: cloud providers → cheap → free/local, with per-provider cooldown and quota tracking. Deployed as Docker container `9router`; fleet reaches it at `http://172.18.0.1:20128/v1`, owner's UI at `http://phon-server.scorpion-tint.ts.net:20128` (Tailscale only).

## Deployment facts (do not reinstall)
- Container `9router`, image `decolua/9router:latest`, `--restart unless-stopped`. The npm CLI binary (`~/.local/bin/9router`) is desktop-oriented — bare run daemonizes into a system-tray mode and dies under systemd; only Docker serves reliably on a headless box.
- Port 20128 published ONLY to three interfaces: the Tailscale IP (owner's UI), 127.0.0.1, and docker bridge `172.18.0.1` (fleet containers). Never republish on 0.0.0.0 — that exposes the dashboard to the home LAN.
- Secrets/env (INITIAL_PASSWORD, JWT_SECRET, API_KEY_SECRET) live in `docker inspect 9router`. Data dir `~/.9router/` (SQLite: `db/data.sqlite`); mount it into the container or state is lost on recreate.
- Settings and keys are cached in process memory — after direct DB edits, `docker restart 9router` before testing.

## Wiring a model provider — via REST API, not the dashboard forms
The dashboard's React forms silently drop JS-set values and close without saving (the outgoing POST carries default payloads). Drive the REST API from a logged-in browser tab instead (`fetch` with the ABSOLUTE URL — relative fetch fails on a non-http origin). The dashboard session expires within minutes; a 401 mid-sequence means re-login and redo the call.

A working provider = TWO calls, both mandatory:
1. `POST /api/provider-nodes` `{"name","prefix","apiType":"chat","baseUrl","type":"openai-compatible"}` → returns the node id (`openai-compatible-chat-<uuid>`). The `apiType` enum is exactly `"chat"` or `"responses"` — anything else 400s with "Invalid OpenAI compatible API type". This call accepts NO apiKey/models fields (extra keys are dropped).
2. `POST /api/providers` `{"provider":"<node id>","apiKey":"...","name":"..."}` — creates the credentials CONNECTION. Without it every chat call fails 404 "No active credentials for provider: <node id>".
- **Prefix names must NOT collide with 9router's built-in OAuth providers** (claude, gemini, minimax, glm/zai, kimi, …). A custom node prefixed `gemini` gets its model resolved to the BUILT-IN provider instead of the node — every call 404s `No active credentials for provider: gemini` (named by PREFIX, not the node id) even though the connection is active and the key valid. The tell: the error names the prefix, not the `openai-compatible-chat-…` node id. Fix = suffix custom prefixes (`gemini-api`, `minimax-api`, `glm-api`), which means DELETE node + connection and re-create — provider-nodes has no PATCH.
- After creating/editing connections via the API, `docker restart 9router` before the first test call — the credential resolver caches connections, not just DB settings.
- Bare local llama-server (no auth): apiKey value `"none"`. Cloud providers: the real provider key.
- Local llama-server (GPU0, port 8080) is reachable from containers via the bridge: `http://172.18.0.1:8080/v1`. The chat model id = prefix + llama.cpp's full model path, e.g. `local-gemma//home/lifetofree/models/gemma-4-12B-it-qat-UD-Q4_K_XL.gguf`.

## Combos (fallback chains)
- `POST /api/combos` `{"name","models":["<prefix>/<model>", ...ordered]}` — OMIT `kind` (null): the dashboard combo LIST renders only kind-NULL rows; a combo POSTed with `"kind":"combo"` is API-valid but invisible/uneditable in the UI (the owner sees the models referenced inside another combo's dropdown yet no row to edit). Fix an already-created one: `UPDATE combos SET kind=NULL WHERE name='...'` + restart. Name is restricted to letters/digits/`-_.` (e.g. `fleet-chain`).
- Invoke a chain by setting the chat request's `model` to the bare combo name (`"model":"fleet-chain"`) — `combo/<name>` or other separators 404 "No active credentials for provider: combo". Upstream errors (402 credits, 403 auth, 429 rate limit) fall through to the next model inside the same request; the response echoes whichever upstream answered.
- Combos have no PATCH — changing the model list = DELETE the combo row then POST the same name again (keep `kind` null).
- Current chain: `fleet-chain` = `kilo-api/anthropic/claude-opus-5.5` (Kilo Gateway — owner's leftover credits) → `minimax-api/MiniMax-M3.1-Flash` → `ag/gemini-3.8-flash` (Antigravity OAuth, FREE) → `local-gemma//home/lifetofree/models/gemma-4-12B-it-qat-UD-Q4_K_XL.gguf` (owner adjusts order in UI: Layers > Combo). `glm-api` is deliberately EXCLUDED — owner reserved z.ai credits for Hermes chat + coding work; composition changes by owner decree, so check the combos table rather than trusting this file.

## API keys
- The middleware enforces a valid key on every `/v1*` path REGARDLESS of the dashboard "Require API key" toggle — treat a key as mandatory; toggling the switch does not open the endpoint.
- Keys in DB, API, and UI are all stored/displayed MASKED (`sk-xxx...last4`) — the full value is never retrievable after creation. Generate one directly instead:
  - `key = sk-{machineId}-{rand6}-{HMAC-SHA256(API_KEY_SECRET, machineId+rand6).hex[:8]}` where rand6 = 6 chars of `[a-z0-9]`, machineId = the install's machineId (stored in every apiKeys row; for this install `204ba68a4b0b3c51`), API_KEY_SECRET = the container env value.
  - Then INSERT a row into `apiKeys` (isActive 1, accessAllow `'[]'`) — validation looks the key up in the DB, a cryptographically valid but unregistered key still 401s — and `docker restart 9router`.
  - The current fleet key is stored encrypted inside the Rakazo credential's secret row — recover it by decrypting that secret (recipe below), not from /tmp; if ever lost outright, mint a fresh one with the formula + INSERT + restart, since any generated-and-registered key works.

## Verification ladder
`curl /v1/chat/completions` with `Authorization: Bearer <key>`:
- 401 `API key required for remote API access` → key absent/invalid (formula mismatch or not in DB).
- 404 `No active credentials for provider: <node id>` → auth fine, missing step-2 connection.
- 200 with `choices` → wired end-to-end; confirm `model` echoes the upstream path.

## Free Gemini via OAuth — Gemini CLI is a dead end, Antigravity works
- **Gemini CLI OAuth connects ("N Connected" in the UI) but EVERY model call returns upstream 403** — a real Google response (verify: router log shows `✗ ERROR 403 · gemini-cli/… · <ms>` with a multi-second upstream POST, not the router's own cooldown message `reset after Xs` which means the request never left). Root cause is account-level Code Assist activation; authenticating the CLI on another machine does NOT clear it for the router's token, and it is a known community issue. Do not re-connect or re-test it — go straight to Antigravity.
- **Antigravity OAuth with the SAME Google account works**: 44 models under the `ag/` prefix — `ag/gemini-3.8-flash` (with -low/-medium/-high variants), Gemini 4 family (argon/carbon/hydrogen/neon), `ag/gemini-3.1-pro-high`, plus Claude opus/sonnet 5.5 tiers; some catalog names 404 at call time (`gemini-pro-agent`, `3.7-flash-low`) — test the exact `ag/` id before wiring it into a combo.
- **OAuth callback replay (remote router)**: the consent redirect targets `localhost:20128/callback`, which is dead when the owner authorises from a phone. Have him paste the callback URL, then NAVIGATE the server-side browser to that full URL — the SPA runs the token exchange and shows "Authorization Successful". A curl or `fetch()` of the same URL only downloads the HTML shell and performs nothing. Confirm via the dashboard provider row ("N Connected"); OAuth connections do not appear alongside apikey rows in the DB connections dump the same way.
- OAuth-backed providers populate the dashboard Quota Tracker; plain API-key providers never do (that page is OAuth-only) — usage/cost for them lives in the Usage & Analytics page instead.

## Token Saver (dashboard) — what to enable for a CONTENT fleet
The savers are tuned for coding-CLI traffic; for a writing fleet: RTK (tool-output compression, matches only git/grep/ls/tree/logs patterns) is safe to leave on but saves little here. NEVER enable Caveman (terse-output prompt) or Ponytail (minimal-code bias) — they inject style instructions into EVERY request and will degrade the fleet's Thai article/chapter output, and output tokens are only ~1% of fleet volume anyway (input is the big side and is mostly cache hits). Headroom (context compression) targets the real bulk (100-360K input requests) but compresses the very text critics/writers must read verbatim — install and A/B test against Benz Critic on one draft before trusting it with content lanes.

## Fleet wiring (Rakazo → gateway) — DONE, write secrets only by this recipe
- Credential: new `user_model_credentials` row (provider `openai-compatible`, label `9router (fleet-chain)`) + its `secrets` row; chain row in `user_model_role_choices` role=`main` position 0 with modelId `fleet-chain` pointing at the new credential. After the glm hard-guarantee (owner reserved z.ai credits for Hermes chat + coding): position 1 = local gemma direct ONLY (glm direct deleted from the chain), and role=`approval` = `fleet-chain` too (was direct glm) — glm is unreachable from the fleet at every layer (combo, connection isActive=0, role choices).
- The secret v2 envelope is TAG-FIRST: `v2:` + base64(salt16‖iv12‖tag16‖ct). Python `AESGCM.encrypt` returns ct‖tag — REORDER to tag‖ct before writing (and pass `ct + tag` to `AESGCM.decrypt` on read). Writing encrypt-output as-is stores a blob the node decipher rejects at RUN time with `Unsupported state or unable to authenticate data` — a host-side readback using the wrong-mirrored layout can still "succeed" and prove nothing; verify with the runtime's layout.
- The secret JSON's `kind` field MUST be `"openai_compatible"` (underscore) for openai-compatible credentials — the secrets TABLE `kind` COLUMN holds `model`, but the api maps `baseUrl` onto the run request only when the JSON field equals `openai_compatible`. Wrong kind ⇒ the request reaches the runtime with no baseUrl ⇒ the static catalog answers `Unknown model openai-compatible/<modelId>` before any HTTP call.
- Required JSON fields: `baseUrl`, `apiKey`, `apiProtocol:"chat-completions"`, `models` map (each entry: contextWindow/maxTokens/images/reasoning), `enabledModelIds`, `contextWindow`, `maxTokens`. Private gateway IPs (172.18.x) pass `assertAllowedOpenAiCompatibleUrl` because `MCP_ALLOW_PRIVATE_ENDPOINT=true` is set in rakazo-api env.
- After credential/chain changes: `docker restart rakazo-api-1 rakazo-worker-1 rakazo-supervisor-1` (credential cache), then verify on the first REAL run (check the `runs` table modelId) — a config readback alone proves the blob only against your own assumptions.
- The dashboard session expires within minutes of login; batch all API calls into one post-login sequence and re-login on a mid-sequence 401.
- SQL `REPLACE(instructions, …)` edits no-op silently on near-miss wording — copy the exact target sentence with `substr(instructions, …)` first, build the REPLACE from that output, and verify with a position() check (dispatch-rule edits failed twice on words present only in the stored text).
