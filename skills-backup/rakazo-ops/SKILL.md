# Rakazo self-host bot ops (~/rakazo, docker compose images)

Durable how-to for debugging rakazo bots. Current sync state / briefs / bot roster live in repo `STATE.md` Infra (SSOT) — read that first for status; this skill carries the inspection technique and git contracts, not the status.

## Where bot state lives
- Bot filesystem state persists in docker volume `rakazo_appdata` mounted at `/data`: `homes/team-*/` (bot team home), `home-revisions/`, `artifacts/`. Inspect WITHOUT touching running containers: `docker run --rm -v rakazo_appdata:/d alpine sh -c 'ls /d/homes/team-*/'`.
- The team home IS the sandbox computer's HOME: `.gitconfig`, `.config/gh/hosts.yml`, browser profiles there are exactly what the bot's git/gh calls read. A credential or helper fixed there applies to the bot's next run.
- Postgres message bodies are sealed (CONTENT_ENCRYPTION) — bot chat text is NOT readable from the `messages` table; diagnose from filesystem homes + `docker logs rakazo-worker-1` instead.

### Verify bot/connection state in Postgres
`docker exec rakazo-postgres-1 psql -U rakazo -d rakazo` (owner creds `POSTGRES_USER`/`POSTGRES_DB` in `.env`; no password inside the container). Live-vs-deleted is SPLIT across tables — query all four before telling the owner a bot is gone:
- `bots` — live bots only; NO `status`/`deleted_at` column, just an `archivedAt` flag.
- `bot_deletions` — the app-level delete log. Empty means nothing was deleted THROUGH the app: a "removed" bot that still appears here was never actually deleted.
- `connections` (external app integrations, has `provider`/`status`) and `agent_connections` (bot-to-bot links) — empty means no integrations are wired.
- `chat_groups` are INTERNAL team chats — never count them as external app connections.
- Wiring/usage map — the question decides the table: `mcp_servers` (its `"healthToolCount"` is the number of TOOLS the server exposes — never read it as a bot or page count) joined with `bot_mcp_servers` (`botId`/`serverId`/`allowAllTools`/`allowedTools`) answers which bots may use which MCP tools; `routines` carries its triggers as columns (`crons`, `webhookEnabled`, `githubEnabled`, `watch`, `messageProvider`, `emailSenders`, `active`, `lastRunAt`) — one SELECT inventories which automation trigger types are USED vs merely supported; split `runs` by `"routineId" IS NULL` to compare chat vs routine activity; model connections live in `user_model_credentials`, bot email in `bot_email_addresses`, cloud coding agents in `cloud_agents`.
- Postgres camelCase columns are CASE-SENSITIVE — quote them exactly as the schema shows (`"secretId"`, `"botId"`, `"serverId"`, `"createdAt"`, `"healthToolCount"`); an unquoted lowercase name fails with `column does not exist`, and while exploring keep stderr VISIBLE (piping psql stderr to /dev/null turns a column-name typo into an empty result that reads as "no rows").
- Verify a column's presence with the bare `col IS NULL` check — wrapping it as `COALESCE(col,'-') IS NOT NULL` is vacuously true (COALESCE never returns NULL) and reports every row as "present"; this once masked a missing spawnKey on a hand-inserted bot and produced a false "structurally identical to working bots" conclusion.
- `runs` has NO name/prompt columns — identify what a run was doing via `LEFT JOIN tasks t ON t.id=r."taskId"` (the prompt lives on `tasks`); a one-shot routine's `routineId` is NULLed after firing, so recently-fired routine runs look like plain runs. `threads` has no `updatedAt` — order threads by `createdAt` or by message count.
- Before calling two config rows "duplicates" or recommending a merge, compare the IDENTITY KEY, not the visible outputs: `SELECT count(DISTINCT "secretId") FROM mcp_servers` plus a join through `bot_mcp_servers` — similar names with the same endpoint and tool count can be two intentional registrations (distinct stored credentials, one bot each); merging them breaks a live bot.

"Delete the bot" is ambiguous by default (Rakazo agent vs Telegram/Discord/Notion bot) — pin down WHICH platform from the DB + token probes before acting on any of them.

## Read before touching
- git operations on volume clones need `git -c safe.directory=<repo>` (clones are owned by UID 1000; host-side git refuses them) — or run inside a container that mounts the volume.
- Prove the credential path before changing it: `.gitconfig` credential helpers determine what git sends (`gh auth git-credential` reads `.config/gh/hosts.yml`; a second `cache --timeout` helper exists). Probe validity WITHOUT printing: sha256-compare the token against a known-good one, then hit `api.github.com/repos/<owner>/<repo>` with it and check `permissions.push`.
- A stale failure report may predate the fix: compare file mtimes (e.g. `hosts.yml`, clone dir) against the failure timeline — the credential may already be correct and the bot simply never retried (its report restates the old error). Re-run the action yourself before concluding it is still broken.
- Push 403 triage order: (1) is the target repo owned by the token's user? (pushing to another user's repo 403s no matter the token) (2) which credential does the helper actually read? (3) API-probe it. Do not mint new tokens while step 1 fails.

## Replicating a sandbox action
- To prove a bot-side action works end-to-end (e.g. a git push), run the computer image itself with the same home: `docker run --rm --network rakazo_app -v rakazo_appdata:/data -e HOME=/data/homes/team-<id> ghcr.io/elie222/rakazo/computer:edge sh -c '...'` — same image + same credential path = the bot's exact path. Throwaway containers on the default bridge can have broken DNS; use the `rakazo_app` network.
- git inside containers: pull `alpine/git` (plain alpine has no git); mask tokens in output with `sed -E "s/gho_[A-Za-z0-9]+/[REDACTED]/g"` before it reaches the transcript.
- The agent cannot enter sudo passwords on this host — when root is required, hand the owner the exact one-liner (install command + what happens automatically afterwards) rather than attempting workarounds.

## Shared Notion API budget (429 bursts)
- The Notion workspace rate budget (180 req/min per connection on non-Business plans, 600 on Business, shared workspace-wide) is drawn on by EVERY integration — Hermes curls and rakazo bot audits compete for the same pool, so 429 bursts land while bots are running, not only from your own loop speed.
- Honor `additional_data.retry_after` and retry the same idempotent request (reads, property PATCHes, body replaces) — never blind-retry a create. When planning bulk audits (e.g. counting child databases under Books Library), pace the queries and RECORD which tables/items were skipped: a silent skip produces a plausible-looking wrong total (the same count run twice with different 429 luck reports different numbers).
- **Endpoint คนละตระกูลห้ามสลับ:** `POST /v1/data_sources/{id}/query` ต้องใช้ DATA SOURCE id เท่านั้น — เอา DATABASE id ไปยิงจะ 404 ทั้งที่ฐานมีจริงและ integration มีสิทธิ์ (ยืนยันว่าฐานอยู่ด้วย `GET /v1/databases/{id}` 2022-06-28 แทน) · และ `POST /v1/search` เป็น fuzzy match — ห้ามใช้นับ coverage รายหน้า (แมตช์คลุมเคลือ) ให้ไล่อ่าน blocks ทีละหน้าแทน
- เพิ่ม/แก้ property บน data source (schema 2025-09-03): ใช้ `PATCH /v1/data_sources/{data_source_id}` พร้อม body `{"properties": {…}}` + header `Notion-Version: 2025-09-03` (ยิงครั้งเดียวได้หลาย property) — `POST /v1/data_sources/{id}/properties` และ version 2022-06-28 จะตอบ `invalid_request_url` ทั้งคู่; relation ใช้ `{"data_source_id": …, "type": "single_property", "single_property": {}}` (ทางเดียว — ไม่เพิ่ม property กลับในฐานปลายทาง ปลอดภัยกับฐานของบอทอื่น); access_token จาก MCP OAuth (mcp.notion.com) ใช้กับ api.notion.com REST ไม่ได้ — คนละระบบ ถ้า integration ไม่มีสิทธิ์ฐานปลายทาง ให้ owner share ฐานนั้นกับ integration ก่อนสร้าง relation · ต่างกันที่ต้นเหตุ: DB ที่ owner สร้างเองใน UI (เห็นเป็น child_database block ผ่าน parent page ที่แชร์อยู่) แต่ `GET /databases/{id}` ตอบ 400 "does not contain any data sources accessible by this API bot" = ฐานนั้นยังไม่เคย Connect กับ integration โดยตรง — สิทธิ์ parent page ไม่ไหลลงมา ให้ owner กด ⋯ → Connections เพิ่มใน DB นั้นก่อน แล้วค่อย query
- Filter BODY shape ≠ schema shape: the schema lists options with `name`, but a query filter must be `{"property": "Status", "select": {"equals": "Promoted"}}` — `"select": {"name": …}` 400s with a misleading `select.equals should be defined` validation error (cost three attempts before the body was read); when a filter 400s, read the raw error body first instead of re-guessing the filter shape.
- Property TYPE is immutable via the API — a rich_text field cannot be converted to relation in place: migrate = read old values → create the new property → backfill rows → `PATCH` with `{"properties": {"Old": null}}` to drop the old one. Creating a rollup requires BOTH `relation_property_name` AND `rollup_property_name` even for `count_values` (omitting the latter 400s). Relation direction matters for rollups: `"single_property": {}` links ONE WAY only and the target database gets no back-relation to roll up over — a two-way pair needs `"type": "dual_property", "dual_property": {"synced_property_name": "<name>"}` (then the synced side appears as a relation property ready for rollups; renaming it via the same properties PATCH works).
- สร้าง database ใหม่ผ่าน API ได้ (`POST /v1/databases` บน parent page — ใช้ page id เต็มจาก search ก่อน ลิงก์ที่ owner ส่งมาเป็นตัวย่อ) แต่: (1) property type `status` **สร้างผ่าน API ไม่ได้** — ใช้ `select` ชื่อ Status แทน (Kanban จัดกลุ่มด้วย select ได้เหมือนกัน) (2) view (Board/Calendar) API สร้างไม่ได้ — ให้ owner กด Layout → Board → Group by Status ใน UI ครั้งเดียว (~10 วิ) (3) ใส่การ์ดตัวอย่าง 1 แถวพร้อมบอกว่าลบได้ — owner เห็นรูปแบบการกรอกทันทีและช่องไหนต้องเติมเองก็ชัด

## Instruction channel reality (updated 2026-11-21)
- No INBOUND messaging integrations exist (no bot email, no personal API key table; auth is session/passkey/SCIM via BETTER_AUTH) — but an owner-session OUTBOUND send is VERIFIED and is the tool for "สั่ง" the team remotely: mint a `session` row, sign the bearer, POST the oRPC procedure `threads.send` — full recipe in `references/rakazo-rpc-send.md`. When the owner is present, pasting the text himself in the web UI (127.0.0.1:5173) is still the fastest path (zero approvals).
- **One-shot routine dispatch (verified across 14 runs, needs no owner and no auth):** INSERT a routine targeting the bot (crons='{@once}', active=true, "nextRunAt"=now(), include "createdAt"/"updatedAt" — `bot_mcp_servers` has those NOT NULL too) — the worker fires it within ~30s and the routine self-deletes after firing (its id is NULLed on `runs`). Judge the outcome from `docker logs rakazo-worker-1 | grep agent.tool.completed` (tool + tool.outcome per call, no error detail) plus the OWNER copying the bot's reply — message bodies are sealed so Hermes never reads them directly; the owner's paste is the richest diagnostic.
- **NEVER dispatch by INSERTing a raw row into `tasks`** (status='queued'): the worker's task dispatch is event-driven through the app API (which also wakes the bot's sleeping computer) — a bare queued row sits forever and bumping `updatedAt` does nothing. DELETE the dead row and fire via the `{@once}` routine above instead (proven: a tasks-table insert for an image job sat 20+ minutes with the bot's computer in `running` state and zero runs, then fired within 30s once re-sent as a routine).
- Batch fleet jobs burn fleet tokens for hours or days — never launch a full queue on your own inference: run a small test batch first, QC it against the command spec, then get an explicit owner go with the cost/duration estimate before opening the rest (a silently running day-long queue on a superseded task is the failure this gate exists to stop).
- An orchestrator's "already dispatched to <bot>" is an UNVERIFIED claim: per-chain hourly message limits make `message_bot` deliveries fail SILENTLY (the orchestrator believes it sent; the target thread stays at 0 messages and no run appears). An orchestrator FINISHING its own run is not a handoff either — a research/compile stage can complete cleanly and simply stop, leaving the downstream builder's thread untouched for the whole day (research landed in the knowledge base, the writer never received anything). After each pipeline stage completes, check the NEXT bot's thread message count and recent runs for the handoff before reporting the chain healthy; when a dispatch is lost or never happened, re-dispatch straight to the worker bot via the one-shot routine above and attach the source pointers (the approved brief, the research page ids, the decided title) so the worker needs no chat context.
- Before dispatching ANY book/e-book/content production task to a bot, verify the referenced volume is the CURRENT project, not a closed one: check the newest briefs in `/home/rakazo/shared/briefs/` (the dated filenames are the project ledger — an old topic reappearing there means the project ENDED) and ask the owner when the only pointer is an old artifact. Dispatching work for an already-finished volume burns a full run and makes the owner re-explain which book he meant.
- Bot-team computer = container `rakazo-bot-team-<hash>`; team work files live at `/home/rakazo/shared/` (briefs, books_library, ebook, manual) — NOT under any git repo by default. `/tmp/rakazo` inside that container is a clone of upstream elie222/rakazo with runtime junk (browser-launch-*, dbus-session, gateway locks) — never commit those.
- Backup pattern for shared work (used 2026-11-20, commit 9b97c30, owner order): inside the bot container, copy `/home/rakazo/shared` into the bot's phon-hermes clone at `rakazo/shared/` (exclude `__pycache__/`, `*.pyc`, secret-like filenames), rebase the clone on origin/main first (it trails main by dozens of commits), commit with honest authorship (`Hermes (lifetofree)`, message states files are authored by rakazo bots), `git push origin HEAD:main`. Owner's standing git-backup rule covers this direct-to-main path; for BOT-initiated pushes the branch-only contract below still stands.

## Creating a bot via direct SQL (verified 2026-11-21, Image Gen bot)
A bare `bots` INSERT is NOT a usable bot — three more rows are required or the owner reports "หาไม่เจอ" / "Bot has no computer":
1. `threads` row (the bot's 1:1 chat — the UI chat list renders from threads): id shares the bot id's first 8 chars + 17 random (25 chars total), `spaceId`/`userId` copied from the bot row, `nextEventSeq`/`nextMessageSeq`/`historyCompactionGeneration` = 0. No thread row → bot invisible in the sidebar even though it exists.
2. `computers` row + `bots.computerId` wiring: kind 'docker', state 'stopped' (supervisor spawns the container `rakazo-bot-<botId>` on first run), 'controlHolder' 'bot', controlFence 0, scope 'dedicated', scopeKey `bot:<botId>`, homeKey = botId, homeRevision `rev-<ms>-<rand8>`, screenGeneration 0, restorePending false. Missing → runs fail with "The model provider returned an error. Details: Bot has no computer".
3. `chat_group_members` rows for every group it should appear in (bot-only groups still need the row).
   - A bot with thread + computer can still be invisible in TEAM views when its chat_group_members rows are missing — the bots API returns every live bot unfiltered and the UI renders team sections from group membership, so diagnose "bot หาย" by checking membership rows first, not the bots table.
- `instructionHistory` must be `'[]'` (empty JSON array, not NULL). Bot id format: `cm` + timestamp + random (25 chars).
- Derive the exact column list from `information_schema.columns` before hand-building the multi-column INSERT — intuitive column names don't exist in this schema (no `deletedAt`, `lastRunAt`, `runCount`, or `section_id`; it's `archivedAt` and `sectionId`), and each guessed-column failure aborts only that statement, leaving later statements' rows committed as orphans.
- After any partial-failure round, clean the orphan children before retrying: `DELETE FROM computers WHERE "scopeKey"='bot:<botId>'` — each failed round leaves a stranded computers row that duplicates on the retry.
- ComfyUI fleet architecture (current): generation runs on the SERVER — `~/ComfyUI` (.venv torch cu130) on GPU1, user unit `comfyui-server`, port 8190, output `~/ComfyUI-Shared/output/imagegen/`; llama-server occupies GPU0 ALONE with the single-GPU fallback model (gemma-4-12B, `-c 262144` = 256K TOTAL split across 4 slots → 65536/slot; `/props` n_ctx reports the PER-SLOT value — reading it as the server's context cost a full re-derivation once; 256K is also the model's native `n_ctx_train` (check via `GET /v1/models` meta) and the VRAM ceiling for 16GB cards — 512K total does not fit). Verified 25 s/render on the RTX 5060 Ti. The Mac's ComfyUI is RETIRED (plists moved to `~/Library/LaunchAgents-disabled/`) — it crawled to 40 min/render under a 27 GB swap explosion (Chrome + CleanMyMac + two loaded models): treat "Mac is slow at gen" as a MEMORY-PRESSURE symptom, not a model problem; `POST /free {"unload_models":true,"free_memory":true}` unloads models to reclaim RAM on a pressured box (they reload on the next job). Porting a workflow between installs requires rewriting the loader nodes' FILENAMES to the target install's files — same model, different quant names (`qwen_3_4b_fp8_mixed` vs `qwen_3_4b`, `ae` vs `z_image_vae`) — list `/models/*/` before firing. Still true: ONE FIFO queue per instance — separate heavy tenants onto separate instances/ports. SDXL mascot-identity prompt rules: identity tokens go FIRST in the positive prompt ("red backwards baseball cap on head, round black sunglasses over its eyes"); NEVER write a "NO helmet"-style negation inside the positive prompt — naming the object there CREATES it (the word "helmet" belongs only in the negative); identity still drifts between seeds — fire 2–3 seeds and pick, or pitch a mascot LoRA (~20 brand images) as the durable fix. When the owner wants to SEE finished images and the bot's closing report lags, scp/deliver via Hermes directly — never make the owner wait on a report for work that already exists.
- Direct-DB instruction edits persist but the owner's UI shows them only after refresh — have the owner pull-to-refresh before concluding an edit "didn't land" (verify from psql first: position + length of the appended section).
- An app-side save can silently REVERT a direct-DB instruction edit (a fleet-list entry added via SQL vanished later while other appends to the same row survived) — before relying on any instruction text written via SQL, re-verify with a position() check at use time; never trust that a past edit is still present.

## Chat-group restructure (chat_groups / chat_group_members)
- EVERY chat_group MUST have a paired `threads` row with its `groupId` set (created when the group is created). A group without its thread crashes `spaces/list` with `IsolationError: Group is missing its thread` (packages/db/src/spaces/groups.ts mapGroup) → status 404 → the mobile app's workspace download fails outright ("ไม่สามารถดาวน์โหลดแอปได้" after logout/login). Fix = INSERT the missing threads row (spaceId/userId from the group row, seqs 0) — the workspace loads again immediately, no reinstall needed. The mobile app renders bots/groups from a sidebar snapshot loaded once per app session — pull-to-refresh only refreshes message lists; stale sidebar = force-close the app or logout/login. `pinned=true` on a bot lifts it to the top pinned section and helps visibility.
- Dissolving a group: delete `chat_group_members` then the `chat_groups` row — its old `threads` row stays as an orphan (has messages, FK-protected); a groupless thread is harmless to listGroups (it iterates groups, not threads) — leave it rather than risk message FK cascades.
- Backup first (`CREATE TABLE _chat_groups_backup_<date> AS SELECT * FROM chat_groups` + same for members), then DELETE members before the group row (FK order) — reversible in one message to the owner.
- Dissolve SUBSET groups instead of pruning them: a room whose members all already sit in the main room is a duplicate context feed, not a function — the function (e.g. critique) lives in a dedicated bot's own chat, not a room.
- Lean-room rule: every member agent reads every room message, so production rooms should hold only the bots that produce in that stream; coordinators and research bots work through their own chats and briefs — an oversize room burns tokens on pure message-processing.
- Prefer a POINTER instruction over inlined rules: point bots at canon files on the read-only `/mnt/hermes-agent` mount plus a curated master index file (e.g. `shared/content-system.md`) that Hermes owns and updates — inlining the same rule text into several instructions guarantees drift, and a stale fleet list in the coordinator is the recurring failure to re-check.

## Instruction audit (all-fleet review)
- Dump every bot's instructions in one shot: `psql -At -c "SELECT b.name || E'\n===INSTR===\n' || b.instructions || E'\n===END===\n' FROM bots b ORDER BY b.\"createdAt\";"` then split on the markers into per-bot files and read them as files — 9 instructions is too much to eyeball in a terminal. Never line-split `psql -t -A` output when a column holds multi-line text (instructions are paragraphs) — pull rows as one JSON aggregate (`json_agg(json_build_object('name',name,'instructions',instructions))`) and parse JSON instead.
- Audit for the recurring stale classes: a coordinator's fleet list missing later-added bots (it cannot delegate to what its instructions do not name — the classic "Chief never hands off" bottleneck); a frozen "current work" section carrying locked page/chapter counts from a superseded project (downstream bots copy the lock into the NEW project's design); failure notes that outlived their fix (a push-403 note after the fix landed makes the bot refuse work it can do); CJK characters leaked into Thai text; host-OS paths (macOS `/Users/...`) that do not exist inside Linux sandboxes; `{"{@once}"}` routines still `active=true` — a one-shot that never fired stays fire-eligible forever and bursts old-project work when dispatch recovers; park them with `UPDATE public.routines SET active=false WHERE crons='{@once}' AND active=true` (owner-approved, reversible).
- Audit also for LANE CONFLATION once the fleet runs split lanes (content articles vs ebook product — see content-system.md Workflows): one lane's audit criteria written into the other's checker (article criteria gating ebook chapters), a tracking bot conflating two status tables (reading-tracking vs production-tracking), and a critic gate applied to the wrong lane — each silently degrades output instead of erroring.
- Full rewrite of a coordinator's instructions (not spot-edits): dump the old text, write the new one preserving every binding directive verbatim, then DIFF ALL bot IDs (regex `c[a-z0-9]{24,32}` old vs new) before deploy — hand-typed IDs are the one silent killer (a single ID typo makes the coordinator unable to dispatch to that bot forever). Deploy large SQL by `docker cp`-ing the file into the container and running `psql -f /tmp/...` — a heredoc piped to `docker exec` without `-i` produces empty output and exit 0 with the UPDATE never fired.
- Owner approval through Hermes counts as the fleet's required approval for instruction edits — state that provenance in the appended text itself. Snapshot first (`CREATE TABLE _bots_instr_backup_<date>_v2 AS SELECT id, name, instructions FROM bots`), then batch targeted `replace(instructions, '<exact stale line>', '<new line>')` per bot, and verify by re-checking lengths + tails. ## Watchdog bridge — monitor bot as eyes, Hermes as hands
When the owner wants "a bot keeps watch and alerts Hermes" (infra health, stuck queues), build it as alert-file + no-LLM cron, never as a bot that acts:
- The monitor bot must run on a DIFFERENT failure domain than the thing it watches — a cloud watchdog dies with exactly the outage it exists to detect, and local-model bots never rate-limit. Verify what the fleet actually runs before designing: bot `modelProvider` columns are usually empty → the deployment default applies (`MASTER_KEY_PROVIDER` in `.env`), and an empty `user_model_credentials` means everything is on the local server (no time limit exists to guard).
- Teach the bot through its EXISTING automation: append a watchdog section to `bots.instructions` (snapshot the old text into a `_stallwatcher_instr_backup`-style table first) and extend the bot's active routine prompt in `public.routines` as one more numbered check — do not create a parallel scheduler. A routine fire only runs the prompt; recurring checks need the routine's `crons` entry.
- Alert protocol: the bot writes a JSON file into the rw mount (`/mnt/inbox/alerts/…json`) and NEVER restarts or touches the watched service — Hermes owns all actuation (systemd, model swaps) and waits for owner approval on restarts. Host-side: pre-create the inbox dir with 0777 (the sandbox writes as a different uid) plus a processed/ sibling.
- Hermes side: cron `no_agent=true` + script under `~/.hermes/scripts/` — scan the dir and exit with empty stdout when nothing is there (empty stdout delivers nothing = watchdog pattern); on an alert, verify from the host yourself (curl the service directly) before delivering, move the file to processed/, and print a short Thai report. Zero LLM per tick means the watchdog itself cannot hit the rate limit it exists to guard.
- Split delivery by SEVERITY, owner decree: error/warning-class alerts go to the owner's chat; routine status/ok reports never reach it (the owner reads routine status where the producer reports it — the watching bot's own thread). Filter in the host script on the alert JSON's severity field with a fail-closed parse (unparseable file = treat as error and relay it). Never re-assign the report accumulator variable after the processing loop — a mid-script `OUT="header"` re-assignment wipes every detail line appended inside the loop (prepend the header to the accumulated body instead); before walking away, test the deployed watcher with mock files of each severity class: info-only must print nothing, mixed must print only the errors plus a skipped-count note.
- Clearing a watcher alert = EDIT the alerting line inside the scanned file itself; appending a status footer does NOT clear it (the scanner greps the whole file, so the original 'รอเจ้าของ/รออนุมัติ' line keeps re-alerting forever). After patching, grep the whole shared dir for the trigger phrase and require ZERO matches before reporting clean.
- A watchdog can RE-REPORT long-resolved items from its own kept context even when every scanned file is already clean — old reports survive inside the newest-N window a trim keeps, and the model retells them as current status. Verify the claimed-broken resource DIRECTLY from the host (HTTP 200 / health row) before believing the report; then inject 'confirmed resolved — do not report again' rules into the bot's ACTIVE ROUTINE PROMPT (read every run) and trim the stale report messages out of its thread — file edits alone never stop context-parroting.
- Keep long-running fleet monitor scripts bash-trivial: a flat loop with plain `[ ]` comparisons only — arithmetic with parameter defaults inside `$(( ))` is where quoting slips in, and a script that dies on a parse error exits at launch (exit 2, near-zero output), silently losing ALL monitoring coverage until something else reveals it; re-verify a freshly deployed monitor produced at least one tick before walking away.
- `docker exec -i` (not plain exec) is required to pipe a heredoc into psql — without `-i` the heredoc never reaches stdin and the query returns empty output that reads as "no rows".
- The health endpoint resolves as `host.docker.internal:8080` ONLY from the api container — bot sandboxes and the supervisor lack that DNS alias, so a bot-side probe can report curl exit 6 (DNS failure) while the service is fine; teach bots to fall back to the bridge IP `172.18.0.1:8080` on exit 6, and verify from the host yourself before treating any bot alert as truth.
- Quota-recovery watcher (same no-LLM cron pattern, every 5 min): decrypt the chain-head credential and POST a 1-token chat to classify OK / QUOTA_OUT / AUTH_FAIL. v2 envelope = `v2:` + base64(salt16‖iv12‖tag16‖ct), key = scrypt(ENCRYPTION_KEY, salt, 32, {N:16384,r:8,p:1,maxmem:64MB}), AAD = the SECRET row's id — resolve it from `user_model_credentials.secretId` first; credential id and secret id are DIFFERENT ids on newer rows and only coincide on old ones (a decrypt that fails with "Invalid initialization vector" is a wrong AAD, not a broken key). The envelope is tag-FIRST (tag16‖ct) but the cryptography AESGCM.decrypt wants ct+tag, so pass `payload[44:] + payload[28:44]`; strip all whitespace/newlines from the base64 and re-pad with `=` to a multiple of 4 before decoding (long psql rows wrap mid-string and a bare b64decode dies with "number of data characters ... cannot be 1 more than a multiple of 4"). Run the node decrypt INSIDE rakazo-api-1 so its deps resolve, and never print the key. HTTP 402 "prepayment credits depleted" (Google AI Studio) classifies as QUOTA_OUT. Probe BOTH the primary and fallback-1 credentials — either one dying forces the whole chain onto the next tier, which is how a "this bot is slow now" complaint actually presents. Alert ONLY on the QUOTA_OUT→OK transition (state file holds the last status). Rakazo re-resolves the chain from position 0 on every NEW run, so recovery-to-primary is automatic — the watcher's job is to TELL the owner, not to switch anything. Write SQL that needs quoted camelCase columns as a stdin heredoc (`docker exec -i psql <<SQL ... - **Owner-facing Notion alerts (Job Desk เงินค้าง/งานค้าง, Content Drafts) run as `scripts/notion-alerts.py` (hermes repo, cron 07:30 ICT) — deterministic code, NEVER the watchdog LLM.** Mechanism that forced the move: after four prompt-patch rounds of accumulating alert rules into the watcher's routine prompt, the model executed 13 notion reads successfully yet still skipped the tail instruction (write a findings file) and re-judged 'ค้าง' against its own definition — prompt rules past ~9KB of accumulated sections are skipped silently, with no error to reveal it. ## Restarting the Hermes gateway (owner request) — NOT from inside the gateway
- `hermes-gateway` is a systemd USER unit (`systemctl --user`) — system-level `systemctl restart hermes-gateway` reports inactive/access-denied and silently does nothing. Cron/systemd-run timers have no XDG session: set `export XDG_RUNTIME_DIR=/run/user/$(id -u)` before `systemctl --user restart`.
- The terminal tool runs INSIDE the gateway process and BLOCKS any command text containing gateway restart (SIGTERM would kill the agent mid-turn) — the sanctioned path is an out-of-tree shell: write a one-shot script (restart `systemctl --user`, log post-state to /tmp, remove its own crontab line + self-delete) and schedule it via cron `* * * * *` (cron executes it as a fully separate session). `at` is not installed; self-SSH loopback fails (no self-authorized key).

## Stuck runs & mass stop/start (token-burn halt)
- "A bot is multiplying / sprouting runs" is usually DISPATCH, not a loop: runs with `trigger='bot_message'` whose source message `clientNonce` matches `bot-message:<runId>:message_bot:<hash>` were sent by ANOTHER bot — join that embedded runId to `runs` to name the sender (typically the coordinator splitting an owner order into pieces) before cancelling anything. Only a self-referencing dispatch chain is a true loop.
- Diagnose a stalled fleet in one query: `SELECT b.name, r.status, count(*), min(r."leaseExpiresAt")::timestamp(0) FROM runs r JOIN bots b ON b.id=r."botId" WHERE r.status IN ('running','queued') GROUP BY 1,2` — per-bot serialization means ONE stuck `running` run blocks that bot's entire queue; after a container restart, `running` rows with `leaseExpiresAt` far in the past and frozen `updatedAt` are ORPHANED leases: the worker loops millisecond `run.continue` jobs on the same run ids every ~30s and never re-adopts them — that wake loop is the LLM token burn, and cancelling runs alone does not stop it (stop the worker first).
- Mass stop on owner order (halt burn now, decide details later): `docker stop rakazo-worker-1 $(docker ps -q --filter name=rakazo-bot-)` → backup `CREATE TABLE _runs_active_backup_<date> AS SELECT * FROM runs WHERE status IN ('running','queued')` → `UPDATE runs SET status='cancelled', "completedAt"=now(), error='<one-line reason>' WHERE status IN ('running','queued')` → `UPDATE public.routines SET active=false`. Keep api/web/supervisor/postgres up — only the worker executes LLM runs, so the platform stays browsable at zero token cost.
- 'ปิดงานทั้งหมด' spans THREE tables, not one: `runs` (status='cancelled' on running/queued/waiting_input), **`tasks`** (a separate work-item table with its own queued/failed/completed statuses — a sweep that only clears runs leaves dozens of stale queued tasks), and `routines` (one-shot {@once} leftovers). Pin the owner's intent first: cancel-with-status (`status='cancelled'`, items dead) vs pause crons (`routines.active=false`, resumable) are DIFFERENT orders — restoring crons is just `active=true`, no rebuild needed. Exclude the watchdog bot's rows (its queued task + cron stay per owner).
- Restart after a stop: `docker start` the same containers + `UPDATE public.routines SET active=true`, then verify the queue stays quiet for a couple of minutes (only push.receipt/messaging housekeeping in `docker logs rakazo-worker-1`) before telling the owner it is ready for new orders.
- Never resume/replay a cancelled queue blindly: those runs are reactions to already-superseded bot messages and re-executing them duplicates cascades — fresh owner orders beat replaying a dead queue.
- `waiting_input` runs are PAUSED awaiting the owner's reply in that bot's chat and sit forever otherwise — cancel superseded ones (`UPDATE runs SET status='cancelled', "completedAt"=now()`) when the awaited work was completed by another path or the context is days stale. And bots showing "not working" between scheduled triggers is NORMAL idle, not a fault: judge fleet health from the latest runs' statuses (completed/failed timestamps), never from a bot's current state.

## Thread growth → "context เต็ม" failure (trim recipe, owner-approved)
A bot thread that accumulates messages (Chief hit 1,896 msgs / 5.5MB) eventually exceeds the model context and the bot answers "context เต็ม" and stops working the task — the run still reports completed, so no watchdog fires on it. Trim = archive-then-delete, NEVER a plain delete: dump the messages beyond the newest 40 to a gzip JSON backup (`~/rakazo-inbox/backups/thread-archive/<threadId>_<ts>.json.gz`), then DELETE by id list — canon/rules live in instructions + content-system.md, so a trim only loses chat history, never knowledge. Automated: `scripts/rakazo-context-monitor.sh` (hermes repo, cron `*/10`) scans ALL bot threads (thresholds 600KB block-text or 400 msgs — lowered from 1,200KB/800 after a 907KB thread still overflowed model context), trims to the last 40, and logs each intervention to `~/rakazo-inbox/alerts/context-trim.log`. One trim dropped Chief 1,896→40 msgs (5.5MB→113KB) and the previously-stuck task resumed immediately; post-trim tool-call pace rose sharply (seconds per call instead of tens) — that speed-up after a trim is itself confirmation the thread size was the cause.
- A "Context size has been exceeded" failure hides from run-status checks: routine-triggered runs carry their own fresh context and keep completing while the MAIN chat thread stays over-full and unusable — completed recent runs do NOT clear the main thread, so trim it (monitor thresholds are KB/msgs, which the model's token limit can exceed first). "Model stream idle timeout" is NOT always transient: check the run's THREAD SIZE first — a bloated thread pushes the prompt past model context, the chain head times out and the local-gemma backup idles out on the same oversized prompt (a 907KB thread failed exactly this way twice while sibling runs on small contexts succeeded at the same minutes); trim the thread, then retry. Only a thin-context run failing this way is a true transient stream stall.
- Standing auto-reaper (owner-approved cron `*/3 * * * *`, script in the hermes repo `scripts/`): clears `running` runs whose lease expired >10 min (or NULL lease and >2h since start) — `status='failed'`, NULL `leaseOwner`/`leaseExpiresAt`; NEVER touch queued/active rows (a legit long render holds a live lease). Write one JSON alert per clear into the inbox alerts dir so alert-watch reports each intervention. After a clear, the worker's ~30s `run.continue` tick starts queued runs automatically — no restart needed.

- **การเช็ค health "Not working" ในหน้า Integrations:** mcp_servers.headers เก็บชื่อ key อย่างเดียว (`{"Authorization": true}`) — ค่าจริงต้องอยู่ใน secrets row (kind='mcp', material `{"headers":{…},"env":{}}`, secretId link, v2 envelope AAD=secret id); ใส่ค่าตรงใน headers แล้ว connector ไม่อ่าน → Not working

## Git contracts with Hermes
- Bots push ONLY their designated branch (e.g. `rakazo/youtube-library` on lifetofree/phon-hermes); never merge a bot branch into main without an explicit owner go. Merge by cherry-picking from a temp `git worktree` to keep linear history.
- After any Hermes-side main push, a bot clone left behind origin/main will non-fast-forward on its next push — record the `git pull --rebase origin <bot-branch>` step for the bot's next run in STATE.md Infra.
- Content bots produce must be secret-scanned before pushing to public repos: grep the staged diff for token patterns (`gho_`, `github_pat_`, `ghp_`, `sk-`, `xoxb-`) and env var names before `git push`.
- If the bot's computer container cannot reach github.com at all (sandbox DNS: generated `resolv.conf` comes out with no nameserver and is read-only inside the container), stop debugging the container and land approved bot work from the HOST via the Git data API: create blobs (base64 payloads with `--data-binary @file`, never inline `-d` — 200 KB files blow the argv limit) → tree on the branch head's tree → commit with parent = branch head (keeps it fast-forward) → PATCH the ref. Then have the bot `git reset --hard origin/<branch>` before its next sync and note that reset in `shared/`.
- Bots hold both the repo mount and vault access, so an agent can DROP files into the tracked repo clone on its own: before committing anything from the repo, `git status --short` and relocate unexpected artifacts — a credential backup (v2-envelope ciphertext) landing in a tracked dir means secrets ride the next push. Move such files intact to a non-repo secrets dir and tell the owner what moved and why.
