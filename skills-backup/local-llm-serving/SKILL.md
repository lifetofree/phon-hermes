# Local LLM serving with Hermes (llama.cpp)

## 1. Persistence: systemd user service, never nohup

- A long-lived `llama-server` MUST be a systemd user service (`~/.config/systemd/user/llama-server.service` — `Type=simple`, `Restart=on-failure`, enabled for boot). Launching it through the terminal tool (background/nohup/setsid) dies when the tool's process scope reaps it: the log cuts off mid-load with no error message, the port never opens, and the PID is gone minutes later — it looks like "still loading" for several minutes before you discover the process is dead.
- PHON-SERVER reference state (2026-11-21): service `llama-server` — gemma-4-12B-it-qat-UD-Q4_K_XL on port 8080, `-ngl 99 -c 262144` (256K total; llama.cpp SPLITS `-c` across parallel slots → `/props` shows 65536/slot — 256K is also this model's native `n_ctx_train`) KV q8_0 + `-fa on`, `--split-mode none`, pinned `Environment=CUDA_VISIBLE_DEVICES=0` (GPU0 only; GPU1 belongs to ComfyUI, user unit `comfyui-server`, port 8190). Qwen3.8-27B-UD-Q4_K_M with the 262k two-GPU split is the REVERT config — the live unit file carries the full revert recipe as comments. Logs: `journalctl --user -u llama-server` (there is NO log file). Health: `curl -s http://127.0.0.1:8080/health` → 200. Read the live unit via `systemctl --user cat llama-server` instead of trusting notes — the served model + flags drift between sessions by owner decision.
- Before `systemctl --user start`, run `pgrep -ax llama-server` and kill any stray manual instance — a bare launch outside systemd collides with the unit on VRAM and port while `systemctl is-active` still reports inactive, hiding the conflict. Kill with `pkill -x llama-server`, never `pkill -f llama-server`: the `-f` pattern matches the invoking shell's own command line and SIGTERMs your own terminal command mid-script.
- Owner rule on this box: do NOT start or restart the server on your own — if it is down, report the state and wait for an explicit go (or get one in the same exchange).
- Config change (e.g. bumping `-c`): edit ExecStart in the unit file → `systemctl --user daemon-reload` → make sure port 8080 is free (kill any ad-hoc instance holding it) → `systemctl --user start llama-server`. Never "restart" by SIGTERM-ing the running PID: that is a CLEAN exit (status 0), so `Restart=on-failure` does not fire and the unit goes inactive — and an ad-hoc replacement you launch outside systemd keeps the port while losing crash-restart and boot auto-start.
- Two reboot gotchas fixed 2026-11-18 (both make the enabled unit crash-loop AFTER a reboot): (1) `--slot-save-path /tmp/llama-slots` dies at arg parsing (`not a directory`) because /tmp is tmpfs — the unit now carries `ExecStartPre=/usr/bin/mkdir -p /tmp/llama-slots`; keep that line when editing the unit. (2) An Ubuntu kernel upgrade can install the new kernel WITHOUT the matching `linux-modules-nvidia-595-open-<newver>-generic` (module metapackage left behind) → nvidia-smi dead, wait-for-cuda times out every attempt. Diagnose: `lsmod | grep -c nvidia` = 0 + `dpkg -l | grep nvidia-595-open` missing the current kernel version. Fix needs sudo (owner runs it): `sudo apt install -y linux-modules-nvidia-595-open-<ver>-generic linux-modules-nvidia-595-open-generic-hwe-26.04 && sudo depmod -a` — no manual start after: the Restart=on-failure loop picks the server up ≤2 min once CUDA returns. Check kernel-version/apt history first when a post-reboot crash-loop shows ExecStartPre timeouts instead of llama-server errors.
- A boot-time crash-loop (unit stuck `activating`, NO llama-server process, journal repeating `start-pre operation timed out`) is usually the GPU driver, not the unit: a kernel upgrade can land WITHOUT the matching `linux-modules-nvidia-<ver>-<new-kernel>` package (HWE metapackages lag the kernel meta; no DKMS on this box), so `nvidia-smi` dies and ExecStartPre can never pass. Run `nvidia-smi` FIRST, before touching unit config. Hand the owner one sudo line installing the per-kernel module package + the nvidia metapackage (`sudo depmod -a` after), then do nothing — the enabled unit's own restart cycle picks up the driver within one restart and starts the server (also the clean way to apply a unit-file edit: change file + `daemon-reload`, let the loop restart).
- A terminal-tool foreground command that runs the server directly (or pipes it) also dies at the command's timeout — and timeout shows as `exit 124` AFTER "listening" already appeared. "Loaded + listening then died without error" = the launcher was reaped, not a server bug. The install that survives: a systemd user unit with `Restart=on-failure` (write the unit file, `systemctl --user daemon-reload && systemctl --user enable --now llama-server`), then verify health 200 + one real `/v1/chat/completions` response. A bare nohup/setsid launch is NOT an install — it dies with the tool's process scope.
- Healthy load is ~6 s (lazy tensor reading); silence past ~30 s means it died, not "still loading".

## 2. Hermes provider config

- custom provider in `config.yaml`: `base_url: http://localhost:8080/v1`, `models:` mapping keyed by the FULL GGUF file path, `models_discovered: true`. The model id is the file path itself, so `model.default` holds an absolute path.
- `llama-server` serves exactly ONE model per instance (`-m <file>`). Ghost models: the picker merges the persisted `models:` catalog with fresh probes, so a model from a previous `-m` lingers and 404s on selection. Fix with `/model --refresh` or hand-edit the mapping; never add duplicate GGUF paths to fake multi-model.
- Two 27B-class quants on 16G×2 GPUs does not fit with a real context — plan one big + one small (two servers, two ports, two provider entries) or accept CPU offload.
- Reserving a GPU for another workload (image gen, etc.): pin llama-server to the remaining GPU with `Environment=CUDA_VISIBLE_DEVICES=0` + `--split-mode none`, switch to a fallback model whose weights + KV fit that ONE card, and shrink `-c` (64k is plenty for a fallback role). Write the full revert recipe (original model path, split-mode, tensor-split, original `-c`) as comments INSIDE the unit file — the next session reads the unit, not session notes. The endpoint and port stay identical so consumers only need their model-id label updated (e.g. rakazo's chain row in `user_model_role_choices`) — llama-server serves whatever model it loaded regardless of the `model` field in requests.

## 3. KV / context fit

- `-c` is the TOTAL context, divided across parallel slots: `/props` `n_ctx` reports the PER-SEQUENCE value after the split, so a "64k" reading can be a 256K server (4 slots × 65536) — read the unit's live argv before concluding the context is small, and state both numbers (total + per-slot) when the owner asks. Before raising `-c`, confirm the model's native ceiling via `GET /v1/models` → `meta.n_ctx_train` (never exceed it — quality degrades beyond training); VRAM then scales ~linearly with `-c` (KV at q8_0 + `-fa on`), giving ~5-6GB headroom at 256K total on a 16GB single card — 512K does not fit there.
- `~/llama.cpp/llama-env/bin/python scripts/kv-fit.py <model.gguf> [ctx...]` prints KV GB (f16/q8_0/q4_0) per ctx from GGUF arch fields. GGUF gotchas: fields are arch-prefixed (`qwen35.block_count`), `ReaderField.contents` is a method, `head_size` may be absent (derive `embedding_length // head_count`), `context_length` metadata = native max (Qwen3.8-27B = 262144).
- Qwen3.8-27B UD-Q4_K_M on this box: ~15.3 GB weights, KV q8_0 ~69 KB/tok (256k ≈ 18 GB; ≈ 32 GB at f16) — fits with RAM overflow (61 GB RAM; slower prefill, works).
- KV must fit FREE VRAM per GPU, not total: GPU co-tenants (ComfyUI, the h3d service ~4.3 GB, desktop) shrink what CUDA can allocate even when they look idle. A too-large `-c` fails per-GPU (`failed to allocate CUDA1 buffer` → `failed to allocate buffer for kv cache`) and `Restart=on-failure` turns it into a crash-loop — stop the unit first to break the loop, then shrink `-c` (64k is plenty for chat/agent work) and add `--tensor-split` proportional to per-GPU free VRAM. Check `nvidia-smi --query-compute-apps=pid,used_memory` before picking `-c`, and read the LIVE `-c` from `systemctl --user cat llama-server` instead of notes — unit flags drift between sessions (notes said 64k, live unit had 128k).

## 4. Cron jobs that depend on the local model

- **A PINNED cron job never inherits the global `fallback_providers` chain** (by design, `cron/scheduler.py::_job_fallback_chain` — a chain entry is a different provider/model, which is exactly what the pin ruled out). Consequence: a job pinned to the local GGUF dies with `RuntimeError: Connection error.` when llama-server is down, no auto-fallback. To get "local first, cloud on failure" leave the job UNPINNED (`model: null`): it follows the main model at fire time AND walks the fallback chain (verify with `hermes fallback list`). State the trade-off when the user asks for this: an unpinned job also follows the main model when it is switched — that is the intended behavior, not a bug.
- **`last_status: ok` ≠ correct delivery.** An agent cron job that gives up mid-run can deliver its own status/progress message as the final response and still be recorded `ok`. Always verify the actual output file (`~/.hermes/cron/output/<job_id>/<timestamp>.md`) for the expected deliverable markers (digest header, item count), not just the status field.
- A local 27B model on a long web-search job fails two ways: looping `web_search` dozens of times then giving up, or "request too large" when another request holds server capacity. On a manual re-fire, pass a transient `prompt` (cronjob action=run) capping the search budget (e.g. ≤12 calls, batched by topic) and demanding the full deliverable as the final response — do not bake that into the job's permanent prompt.
- Manual re-fires are deduped: if the job is already running, the run is skipped with an explicit `execution_skipped` note — that is not a failure, do not re-fire again.

## 5. When the target server serves THIS session

- Before restarting any llama-server, check whether it is the one serving the current session (config.yaml `base_url` vs `ps aux | grep llama-server`). If yes: do NOT restart it — the session drops; give the user the exact kill+restart command to run after, or let them choose the trade-off.
- Determining the session's own model is subtle: the gateway session has a model in its config, but a mid-session provider switch (e.g. to glm-5.3-flash via Z.AI) means the session is NOT on the local server even when config.yaml still lists it as primary — a stale-config restart is safe in that state. When unsure, ask.

## 6. Downstream consumers (not just Hermes sessions)

- Context-limit COPIES drift downstream after any `-c` change — the server's `/props` `default_generation_settings.n_ctx` is the only authority. Each consumer keeps its own stale copy: Hermes caches per-model values in `~/.hermes/context_length_cache.yaml`, and third-party gateways store a per-connection limit in their own config (rakazo keeps it inside the connection's ENCRYPTED credential blob — editable ONLY via its UI Advanced field, unreachable from its database). When the owner reports "context is X but should be Y", verify live argv + `/props` first; if the server already serves the requested value, the fix is the downstream copy in that consumer's own settings — do not touch the unit and do not restart.
- Check what else points at port 8080 before declaring the server optional: pinned/unpinned cron jobs (see §4), user services (`systemctl --user list-units | grep llama`), and other profiles' provider configs. A restart that looks safe for THIS session can still kill a scheduled job's next fire window.
- After any restart, verify the FULL chain, not just health: health 200 → `/v1/models` returns the expected model id → one real `/v1/chat/completions` call returns non-empty content. After a flag change (e.g. `-c`), also prove the new value took: `/props` → `default_generation_settings.n_ctx` plus the live argv (`systemctl --user show llama-server -p MainPID --value` → `ps -o args= -p <pid>`) — health 200 alone does not. A thinking model with a tiny `max_tokens` returns empty content + `finish_reason: length` — that is the reasoning budget being consumed, not a failure; re-test with a larger budget before diagnosing.
